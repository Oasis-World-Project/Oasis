# 自主规划集中验证

- 日期：2026-10-27。
- 状态：六例真实验证与独立成品检查已完成（2026-10-27）。全部自主交付；两例严格通过、一例主体通过但有小问题，三例有明确缺陷，不宣称六例质量全部通过。
- 目的：在继续 5.9 前，验证系统能否仅凭业务目标组织工作、使用已有能力并交付。不是增加一种业务工作流，也不替代 5.7 的独立收尾。
- 依据：ADR 0003–0006、0008–0010，以及用户本次关于陌生任务、跨领域组合、同类任务改变约束的要求。

## 执行位置与用户设备

ADR 0003 明确执行一律在服务端。调用生图、生视频、音乐等供应商 API 时，模型推理在供应商运行；Oasis 的规划、节点运行、文件处理、媒体合成与检查在服务端执行器运行。调用模型不等于所有加工都由模型供应商代劳。5.9 的云 GPU 执行器和具体供应商尚未接入，不能写成已可用。

用户端承担 Web/Electron 界面、工作流图与成果展示、音视频解码播放、文件选择/传输和桌面同步。大量节点、大文件、较高分辨率视频会受客户端 CPU、内存、显示能力、磁盘与网络影响；这些不是模型推理或离线渲染的硬件要求。5.7 的可运行成果在隔离服务端运行，用户接收画面/音频、发送操作，体验也受网络延迟影响。3D 查看器的具体交互渲染位置尚未设计；若采用客户端 WebGL，展示流畅度会受终端 GPU 影响，不能提前承诺所有 3D 展示与本机性能无关。

当前本地开发把九个服务、Docker 沙箱和中间件运行在开发机上，开发机实际兼任服务器，因此其 CPU、内存、磁盘和网络影响任务执行。部署后这部分资源由 Oasis 服务端承担。云 GPU 是任务执行能力，和项目以后整体迁移 Kubernetes/云原生运维并非同一事项。

## 验证方法

1. 冻结当前代码与手册基线，不为案例预先补提示词、模板或命令。现有手册照常参与选择；“陌生”指业务问题未专门开发，不声称文档/数据等基础格式完全不匹配手册。
2. 六例分别创建独立会话，经正常 gateway 入口完成素材上传、需求澄清、任务单确认、动态规划、执行、关卡和画布交付。不直接提交工作流或人工编写节点。以当前默认聊天角色进入需求澄清；节点模型与工具由系统自行选择。
3. 输入只包含目标、素材、使用者、交付要求和限制。允许输出格式、片长、来源要求等用户可理解的约束；不提供节点数、角色分配、模型、命令、内部工具名和产出路径。
4. 素材使用明确标注为测试的虚构数据及自制媒体，包含可核对的输入摘要。检查答案和内部评分规则单独保存，不作为制作步骤交给 AI。资料问题只按预先声明的事实回答，技术追问使用默认/自行决定；任务单遗漏硬性要求时记录为需求理解缺口，不暗中修好再算首轮通过。
5. 每例保存原话、素材摘要、问题及答案、确认任务单、原始计划、节点/工具实际调用、自动修订、关卡、成品摘要、费用和人工介入。独立成品检查来自实际文件，不以节点自述、task 的 succeeded 或模型打分替代。
6. 允许系统既有自动重试、关卡退回和模型地区回退，单独统计。人工补命令、改节点、换模型、改代码或手册后完成的，标为“人工介入后完成”；原始失败证据保留，修复后另开复测，不覆盖首轮结论。
7. 不要求多节点或多模型越多越好；比较必要依赖、职责、工具和交付内容是否适应约束。两个计划节点数相同也可能合理，只有节点改名不算适应。六例全过仅证明这些样本，不证明任意任务可靠完成。

## 结论与停止条件

逐例记录：需求理解、计划合理性、依赖/文件传递、能力选择、约束保持、独立质量检查和交付完整性。分类为自主通过、自主交付但未达标、人工介入后完成、环境/能力阻塞、费用边界停止、未检查。不把预算暂停、供应商不可用或不支持的 5.9/5.10 能力混称为规划失败。

当系统进入需要处理时，保存原因；基线不通过人工补步骤继续。正常 task succeeded 仍检查 warnings/unchecked 与成品。新增 3D/GPU、数字人、外站浏览器和 Android 接入不在本轮补齐，5.7 的未完成事项依 ADR 0009 跟踪。

### 三组对照说明了什么

- 排班组没有专用排班手册，系统仍实际读取素材、求解并区分可行和不可行；两例图拓扑相近是合理结果，关键是无解分支的判断、缺口与条件调整发生了变化。普通文档/数据手册依然可能被选中，不把它误称为完全没有任何手册。
- 筹备组的节点数量同为 5，但第二例实际增加了联网证据与汇率依赖，使用了不同的输入、工具及合并顺序，并非只改节点名字。也同时暴露了澄清阶段错误假设会被后续团队放大：接需求目前只知道附件文件名/大小，B2 提前定了人民币和额外估算项。
- 媒体组由复用已有素材的 2 节点，变为补图片/动态画面/音乐的 5 节点；本轮未人为指定视频生成模型，也未要求一定调用收费视频工具。C2 选择代码动画与本地音乐合成，符合已有能力和费用限制。这个结果证明本样本的组合能力，不证明拆成 5 节点就是最优安排。

### 2. 任务单：保留原始约束，先读材料再决定

**受限素材读取。** 在第一次生成问题/任务单前，由 conversation 经内部 HTTP 请求 harness 对已核对所有权的上传材料做正文解析。拟新增 `POST /internal/materials/inspect`，只接收所有者、上传 ID 和受限解析参数，不接收任意 URL 或宿主机路径；harness 通过 canvas 的 lookup/content 接口取原文件，核对大小和 SHA-256，复用 `file-inspection` 的 worker、超时、解压、页数、单元格和字符限制。不跨服务 import，不为读取材料伪造一次 agent 运行。

返回每份文件的上传 ID、摘要、提取文本、定位信息、解析状态和截断原因。纯文本/CSV 至少能定位到行或提取文本片段；已有格式复用现有解析器，不在这一批建设所有格式的 OCR、音视频理解系统。图片和视频的元数据不能冒充读懂内容。超限、未支持、损坏、超时分别记录；看不到的内容保持未知，不能从文件名推测币种或费用。若确有必要使用视觉或其他模型理解，仍走 model-gateway 计费并受原预算约束。

解析结果按上传摘要和解析版本在当前 intake 的 JSON 记录中复用，避免每轮重复处理；材料变化就失效，不能全局复用其他用户的文本。正文以材料数据传入模型，不能改变系统指令、权限或工具范围。解析结果持久记录覆盖范围，原始文件继续由 canvas 保管，不把完整附件拼入 20,000 字的 brief 后静默截断。

**默认选项由代码解析。** 对 `auto`、直接开始时未答的问题，使用那一轮已保存的 `question.default` 找到具体 option ID 和 label。原始答案保留，同时交给模型和 task 的是“采用该题默认项：X”。普通自由文本仍按原话处理。不存在的默认 ID 必须校验拒绝，不能临时另选；如果模型推荐的默认项本身违背原硬约束，任务单校验仍应发现，`auto` 不表示用户撤销了原限制。

**约束和假设分开。** 在现有 `TaskSheet` 增加可选的结构化 `requirements`，每条有稳定 ID、要求原文/准确归纳、来源引用。来源可指向原始需求、用户后续发言、某轮具体选择，或附件的上传 ID、SHA-256、定位及短引文。它记录本次有效约束；撤回历史保留在 intake turns，不再执行。`criteria` 继续表示如何验收，`assumptions` 继续表示 AI 的制作选择，两者引用要求而不能另立相冲突的事实。

优先关系是：用户明确的后续修改覆盖被其明确修改的旧要求；其他原始要求继续有效；相关附件事实进入要求依据；默认选项和 AI 假设只能补空白。附件和用户原话冲突时，在既有澄清轮次内问清业务问题；已经无法追问时保留冲突和缺失，不能自行声称已解决。普通“确认任务单”不应成为 AI 偷改原约束的免责依据；真正的要求变更要能追到用户的话或明确选择。

**生成后检查，确认后冻结。** 在现有 intake JSON 校验/重试路径里增加来源存在、引文对应、默认答案、预算字段等确定性检查；再检查是否遗漏、强化或扩大原要求。后者涉及自然语言，应使用有来源证据的语义检查，不能宣称代码能证明所有自然语言等价。缺失或矛盾交回现有重试流程修正，不增加无上限模型循环；仍不能解决时明确报整理失败或未明确项，不把不合格任务单当成功。

用户确认后，task 保存同一份有效约束快照，规划、首次执行、重试、继续和关卡都使用它；不允许只有 planner 看过、worker 和 gate 又只剩自由摘要。`taskBrief` 改为区分“用户有效要求”和“AI 制作选择”，保留原话及明确撤回记录。任务单 UI 展示简洁的原限制、AI 假设及未读材料提示，来源细节可展开，不要求用户阅读内部 ID。

B2 应保留“按附件报价的小计加 10%”这一口径；交通核实不等于授权添加交通补贴、茶点或改用市场报价。B1 应保留“中文为主”，不能强化成“全部字符必须为中文”。这些是通用的范围保持规则，不写 B1/B2 专用分支。

### 3. 检查器：按证据检查每条要求

**检查职责。** 保留 `checks` 自然语言入口，允许其元素由旧字符串扩展成带 ID、要求引用和证据引用的对象；task 内部归一为同一种检查结构。证据引用只能指向本节点输出、授权材料或图中可取得的上游输出，不能访问未授权路径。规划门检查引用存在、依赖可达和职责合理性。节点关卡检查当前节点能完成的事；跨交付物人数/日期/预算一致性由具有输入的汇总节点或最终验收检查，不要求并行的单文件生产节点凭空证明其他文件一致。

每条结果至少保留检查 ID、`passed` / `unmet` / `unchecked`、原因和证据范围；原 `unmet`、`unchecked` 数组从这些结果生成，继续支持现有消息。缺证据、解析超限或未支持表示 `unchecked`；确认损坏、缺文件或可证明的约束冲突才是 `unmet`。一个 ZIP 尚未解析不应取消其他可独立检查的 Excel 算式、MP4 时长等结论；但需要该 ZIP 的检查仍不得判通过。按证据分组批量调用现有决策模型，避免变成每条一个新调用。

检查范围包含有效用户限制，不能只看可能遗漏原要求的 `sheet.criteria`。来源事实、结构化规则和语义判断分层：数量/尺寸/路径/摘要/可解析性用代码；内容是否符合目标用语义证据；版面完整性用实际渲染或视觉检查。节点自述仅作说明，不能作为“文件已经包含”的证据。对于“正好 N 个”，未知文件也要计入可能的数量上下界，不能把“超过 N 但有文件未解析”判为通过。

**MLT 合法性。** 去掉把固定 basename 当成有效性的条件；同目录的合法 `.mlt` 别名可以检查。继续拒绝符号链接、路径越界、远程资源、不符受支持 timeline 的 XML、摘要不符和超限内容；检查仍必须找到配套 timeline、字幕和媒体。`check/render/pack` 与受信 `media-check` 使用一致规则；打包时明确保留承诺的文件名或生成对应说明，不能检查接受别名而 pack 又硬编码遗漏它。单独下载的 MLT 没有配套资源不算“完整工程”，完整交付闭包仍需一起验证。

**真实版面与工程表现。** PDF 文本抽取不等于页底没有裁切；将版面要求分配给会实际渲染和检查成品的节点，未知覆盖留明。媒体先用冻结工程定位 Windows/Linux 下字体可用性、字号单位及动态文本参数差异；原因确认后修 `project_xml`，采用经过两端验证的参数并说明字体依赖。不能先断言必然是字体回退，也不能通过删除测试标记或把全部可编辑文字压成图片来过关。没有字体时说明缺失；不默认在用户电脑安装字体。独立 GUI 重导出仍是本批验收证据，不把解码通过等同于视觉保真。

用户界面和私聊措辞同时校正：有 `unmet` 时突出“有未满足项”；只有未检查覆盖时突出“部分未完成检查”，不能只显示“做好了”而把所有限制藏在过程提醒里。工作流 `succeeded` 状态语义不变，也不声称为所有未知情况提供质量保证。

### 4. 最终交付：先算实际清单，再核对说明

**一个解析入口。** 继续由 task 的 `output-files.ts` 负责匹配，conversation、canvas、桌面同步和整包下载消费同一份最终结果。明确向规划员、执行员和节点编辑界面说明：`素材包/*` 只包含一层；`素材包/**` 包含嵌套文件。现有实现已支持这一区别，本批补契约说明及漏交检测，不再引入第二种 glob 语法。`expects` 可以包含内部中间产物，不强制全部变成用户交付。

**逐项核对。** 新任务中每个明确 `deliver` 选择器都必须匹配至少一个有效非空文件；零匹配不能因同一节点还交了 MP4 就被隐藏。多交付物共用一个节点时，仍逐项核对任务单中的形式与实际产出，不能把“owner 存在”当成“每种交付物存在”。最终负责人运行完成后先做候选清单核验，缺少项可在原有的一次节点重做中修；最终验收再次对实际清单核对，若仍缺失按原规则记 unmet 并如实交付，不自动开启另一轮制作。

文件记录复用已有 `RunOutputFile` 的大小和 SHA-256，并在对外最终清单保留产出运行 ID、节点与路径的绑定。重试后只能引用最终采用的运行，不得混入旧草稿。现有 `deliverables.files` 已能持久保存采用文件；在此基础上生成清单，不新建平行文件表。新产出应有摘要，历史无摘要记录保留未知，不能补造摘要。

**包内容与外部依赖。** 扩展受限文件检查以取得 ZIP 的真实成员清单、大小、摘要和错误，限制成员数、解压总量、路径和链接，不执行包内脚本。工程检查从 timeline/工程引用核对媒体闭包；普通素材包则核对已声明内容。`oasis-media pack` 本身只承诺工程、字幕和引用媒体，不把它误当作会自动包含任意制作脚本的通用归档器。需要交脚本时由执行员显式选择目录或制作包含它们的素材包，再核对成员。

**交付说明。** 系统交付卡的文件清单从上述结果生成，不沿用节点口头列举。节点制作的 README、报告等也对照最终清单和真实包成员检查“已附带 X”的声明：承诺的路径不存在就是缺口；无法读完则标未检查。自由文本声明仍需要语义判断，不能声称能用正则穷尽识别。修正尽量在负责人尚可重做时完成，结束后不悄悄修改成品或已确认要求。

新计划可以少作不必要的承诺，不能收缩用户要求：C1 原需求没有指定旧任务单中的工程别名，新版可选择规范名或合理的完整工程 ZIP；若承诺独立 MLT，则必须交付并带齐所需资源。C2 原需求没有要求额外制作脚本；不承诺它们是合理选择，但必须交付可再编辑的完整工程及素材，不能说明写“脚本已附带”而实际没有。

### 5. 模块、数据与实施顺序

按以下顺序完成同一批修复：

1. 先固定失败回归夹具和预期：错误默认解析、约束漂移、MLT 别名、单层目录漏交、未检查误判和跨平台文字。夹具来自既有证据，只放进测试，不注入生产手册。
2. 先更新契约读取能力及旧数据兼容，再实现素材上下文和要求来源；随后贯通 planner/worker/gate，避免只有入口修好。
3. 修检查规则和媒体契约；再做交付候选核验、最终清单和 UI 提醒。检查与清单共用路径解析和报告，避免两边给出不同答案。
4. 完成不调用真实模型的测试、真实软件免费验证与工程检查，固定修复提交/摘要；最后一次性用原输入跑六例真实复测。

计划不新增服务、表或依赖。需求来源放在现有 intake turns / task sheet JSON，节点检查放 config，采用文件放 deliverables，检查详情放 acceptance；无 SQL 结构变更时 Expand/Migrate/Contract 不适用。旧任务没有新字段时按原资料显示“不具备来源/检查详情”，不改写历史结论；旧 `checks` 字符串归一处理，旧缺省 deliver 与显式空清单的区别保留。先部署能读新形状的消费者，再启用新写入，不能假设 Zod 会保留未知字段；检查读取、转发、持久化和消息序列化全链路。如果实施发现确实需改表，先补迁移设计，不暗中扩表。
