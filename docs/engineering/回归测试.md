# 回归测试、任务追踪与验收模式

- 日期：2026-11-08（阶段 0「安全网」）。
- 目的：以前没有一条自动化测试从「发任务」跑到「画布里打开成果」，单元测试用假实现全过，真链路第一次跑就是用户手动验收。现在本机一条命令就能把整条链路跑一遍；以后每次验收失败，先写成回归用例再修。
- 规矩：每个阶段（见执行方案）回归全绿才进入下一阶段；改了 task、harness、model-gateway、inspector、canvas、conversation 的行为，提交前跑一次 `pnpm e2e`。

## 命令

| 命令 | 做什么 | 花钱 |
|---|---|---|
| `pnpm e2e` | 跑全部回归场景（假模型、真容器、真画布），大约 2 分钟 | 不花 |
| `pnpm e2e web revise` | 只跑这几个场景 | 不花 |
| `pnpm e2e --keep` | 跑完不停服务、不删任务，方便用 `pnpm trace` 和日志排查；Ctrl+C 结束 | 不花 |
| `pnpm e2e --real` | 真模型、真工具跑 3 个小场景，每个场景（含接需求和聊天）花费上限 $1，超了当场取消任务、判失败 | 2026-11-08 实测：网页约 $0.08、修改约 $0.07、生图约 $0.28 |
| `pnpm trace <任务 ID>` | 一个任务的每次运行、模型和工具调用、算力、关卡提醒、费用来源、画布成果，并标出异常 | 不花 |
| `pnpm accept` | 验收模式：服务从当前代码启动后不再跟着代码改动重启，Web 用构建好的版本 | 按实际使用 |

`pnpm e2e` 和 `pnpm accept` 都要先停掉 `pnpm dev`（端口冲突时会直接说）。需要 Docker、`pnpm env:init` 生成的 `.env`，以及沙箱和检查浏览器镜像（`pnpm sandbox:build`、`pnpm browser:build`）。

## 回归里哪些是真的

- 真的：10 个服务（直接用 node 跑 `src/main.ts`，和 `pnpm dev` 同一份代码和 `.env`）、PostgreSQL / NATS / SeaweedFS / Mailpit / Valkey、沙箱容器和 dsh、浏览器检查容器、画布、Web 前端（Vite 开发服务器）、桌面外壳（Electron，隐藏窗口）。
- 假的：模型供应商。`scripts/e2e/fake-provider.mjs` 是一个 OpenRouter 兼容的本地服务，按场景脚本回答；生图、生视频交固定的测试图片和测试视频（视频由沙箱镜像里的 ffmpeg 现做一次，缓存在 `.tmp/e2e/fixtures/`）。Tavily、FAL、Runpod、BrowserStack、LiveAvatar 的密钥在回归里置空。
- 用户：只经 gateway 的 `/api/*` 说话（Cookie 登录、Origin 校验照真的来）。每个场景一个新测试账号（`e2e-xxxx@example.test`），验证码从 Mailpit 取；私聊里「发任务」→ 任务单 → 按标准档确认 → 等任务结束 → 看画布。
- 收尾：删任务（真删除），并确认画布按删除事件把成果清掉。上一轮中断留下的任务，下一轮开头用当时的测试账号取消并删除。

一轮的顺序：检查镜像和端口 → 中间件（都健康就不动）→ 构建共享包和桌面端 → 起服务（模型网关指向假供应商）→ 核对开发库表结构和迁移文件一致 → 起 Web → 清理上一轮遗留 → 普通场景并行跑、会重启服务的场景排在后面一个个跑。沙箱和检查容器各限 1 核，同时最多 4 次运行。

输出在 `.tmp/e2e/<时间>/`：`logs/<服务>.log`、`calls.jsonl`（假供应商收到的每次请求，边跑边写）、`report.json`、`canvas/<任务>/`（桌面端画布回归的 `electron.log` 和隔离框里的页面）。

## 场景

| 场景 | 覆盖 | 断言要点 |
|---|---|---|
| `web` | 多文件网页（ES 模块互相 import）→ 浏览器关卡发现计数错 → 退回修一次（修好后节点用 `app.check` 自查）→ 桌面端画布里打开 | 退回 1 次、没有提醒、修复提示带着关卡发现的问题；自查经沙箱 → 模型网关 → inspector 跑通；浏览器检查的算力结算在任务上；下载的检查报告是修好后通过的那次、带首屏；画布里文件齐全；在真的桌面外壳里按测试计划点一遍（隔离框只给脚本权限） |
| `testplan` | 测试计划放错目录 | 关卡明确说「oasis-test.json 放在了 out/…」并退回，节点挪好后通过，不能悄悄当成没写测试 |
| `manifest` | 网页交付了却没配 `oasis-app.json` | 关卡退回让节点补上清单，补完画布里能运行（ADR 0017 §5） |
| `media` | 生图工具 → 下游节点用上游的图写 DOCX | 生图请求到了供应商；画布里的 PNG 和测试图一致；DOCX 里嵌着图 |
| `revise` | 修改流程：规划员排方案 → 等确认 → 沿用 / 重新做 / 接着原会话改 | 方案对；沿用的节点不再调模型；第 1 版冻结可查；画布原地更新、不多出一份 |
| `stop` | 节点跑命令时用户停止，马上继续 | 一次停下、一次接着原会话做完；报告进画布 |
| `workspace` | 第一版交付后节点的持久卷被清掉，再要求接着原会话改 | harness 拒绝接着原会话，task 改成重新开会话做、带上 `in/_previous/`；那次接不上的运行记成失败、写明原因，节点不失败、不留提醒；画布里是在上一版基础上改的 |
| `video` | 长任务工具：生视频要 `oasis-tool wait` 等结果 | 提交、查询、取内容都发生；画布里的 MP4 和测试视频一致 |
| `fault` | 流断在半路、输出被截断 | 都不能当成做完；两段都交付；流断掉的调用按供应商实际花费结算，不按字数估 |
| `takeover` | 节点跑命令时 harness 崩溃重启 | 在原来那次运行、同一个会话里接着做；被打断的命令重做一次 |
| `gateway` | 模型回答到一半 model-gateway 崩溃重启 | 任务照样交付；卡住的调用（快进 31 分钟后）被收尾、冻结退回 |
| `real-web`（`--real`） | 真规划员、真模型做计数网页 | 交付、画布里有可运行的网页、桌面端画布里点一遍 |
| `real-revise`（`--real`） | 真模型写短文 → 提修改 → 确认 → 第二版 | 第二版在画布里原地改好 |
| `real-image`（`--real`） | 真的生图工具 | 画布里有一张真图片（格式和大小） |

每个场景同时检查假供应商的「协议违规」：请求的输出上限超过模型真实上限（65,536）、看不懂的请求，都算回归失败。

## 回归第一次跑就发现并修好的问题（2026-11-08）

1. **开发库表结构和迁移文件不一致**：task 库少了 `nodes.retired_version`——迁移记成已执行，文件却在执行后改过（dbmate 只记版本号）。确认任务单时 502。已补列；回归和验收模式开头都做表结构核对（每个服务在临时库里跑一遍迁移，逐列比较）。
2. **停止后马上继续会失败**：那次运行还在收尾（停沙箱、存会话），harness 当成「还没结束」拒掉，节点失败、会话被取消。改为等它真正停好再接着（`services/harness/src/service/run-service.ts`）。
3. **几个人同时发任务会把 conversation 的连接池占满**：会话锁用的是会话级 advisory lock，每轮回复占一条连接直到模型答完，发任务时消息锁和接需求锁各占一条；6 个人同时发任务就占满 10 条连接，别的查询 3 秒拿不到连接，接需求失败。改成 `conversation_locks` 表里的租约行（持有期间每 10 秒续一次，进程崩了 30 秒后失效），持锁不再占连接（迁移 `20261108130000_conversation_locks.sql`，真实数据库测试覆盖）。
4. **网页交付了画布里却打不开**（真模型回归）：规划员有时没把 `oasis-app.json` 写进网页节点的要求，节点交出网页没有清单，关卡没跑浏览器检查就放行，画布里也不能运行。关卡加了一条确定的规则：交给用户的网页没配清单就退回节点补上（ADR 0017 §5，回归场景 `manifest`）。
5. **桌面端画布回归自己的竞态**：外壳先打开首页、失败会每秒重试，测试紧接着跳画布会被它打断（ERR_ABORTED）；改为等首页加载完再跳。修改后画布原地更新成果有延迟，断言改为等内容更新。

还记下、没改的：

- 关卡一次只报出眼前的问题，只退回一次：测试计划放错时只报这一条，挪好后才会发现网页本身的错，而那时已经不能再退回，只能带着提醒交付。可以考虑测试计划放错时照样按它执行、一次报全。
- harness 重启接管后，持续目标的续跑不带「恢复」提示，模型只看到「unknown job」再自己重做那一步；能做完，但提示可以更明白。

## 写新场景

场景在 `scripts/e2e/scenarios.mjs`：任务单（`title`、`deliverables`、`criteria`）、规划员交的方案（`plan`，修改时 `revisionPlan`）、每个节点在各段里怎么做（`nodes`）、用户怎么操作和断言（`run`）。

- 用户原话里带标记 `[[e2e:场景@本轮编号]]`，节点目标里带 `[[e2e:场景@本轮编号/节点]]`，假供应商据此找到脚本；上一轮的编号直接拒单，旧任务不会混进来。
- 节点的会话按提示词开头分段：`work`（开始干活）、`rework`（关卡退回）、`resume`（停下后继续、中断后恢复）、`revision`（修改时接着原会话改）。每段一组步骤：`{ bash }` 跑命令（`writeFiles` 帮你写文件）、`{ tool, args }` 调别的工具、`{ text }` 直接回答；步骤也可以是函数，按提示内容决定怎么做。
- 故障：步骤上加 `fault: 'disconnect' | 'length' | 'error500'`（流断、截断、上游 500）或 `hang: true`（不回答，等调用方断开），每个位置只触发一次。
- 一段的步骤做完后，假供应商自己 `get_goal` → `update_goal complete` 结束这一段（关卡退回段直接回一句话）。
- 会重启服务的场景加 `serial: true`，排在最后一个个跑。

## 任务追踪

`pnpm trace <任务 ID>` 只读本机开发库和 Docker，不改任何东西。列出任务状态和花费（对比预估）、规划员那次运行、每个节点每次运行（harness 状态、用时、产出数、工具调用数、是否经历过接管、错误、调用按种类和费用来源汇总、失败调用的原因）、画布成果。标出的异常：

- 模型或工具调用按估算扣费（算力本来就按核数 × 实际时长计价，不算异常）；
- 调用卡在「进行中」超过 5 分钟；
- 调用结束了冻结还没退回；
- 运行结束了沙箱容器还在；
- 任务记的花费和调用合计对不上；
- task 记着、harness 里却没有的运行。

有异常时退出码是 1，可以接在脚本里用。

## 验收模式

`pnpm accept` 起中间件、构建共享包和 Web，再从当前代码起 10 个服务，Web 用 `vite preview` 跑构建好的版本（`/api` 照样转到 gateway）。之后改代码、改共享契约都不会让服务重启，在途的任务不会被打断（11-08 改契约让 `pnpm dev` 全部重启、丢下了在途的调用）。要换成新代码就 Ctrl+C 后重新 `pnpm accept`。桌面端照常 `pnpm desktop`。模型走真实供应商，花的是真钱。日志在 `.tmp/accept/<时间>/`。
