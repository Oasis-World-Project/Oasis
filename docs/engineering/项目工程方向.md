# 项目工程方向与原则说明

> **文档用途**：本文档用于向参与本项目的 AI 开发助手（或新加入的工程师）一次性、无歧义地传达项目的工程定位、架构约束、技术选型原则与开发工作流。阅读本文后，应能立即理解“这个项目要做什么、不做什么、为什么这样定、以及每个决策的边界在哪里”。

---

## 一、项目一句话定位

**一个以 DeepSeek Harness 的工程技术底蕴为底座、经过业务化改造的桌面端 Agent 产品，采用微服务架构、本地优先开发、云原生就绪的工程体系。**

三个关键词缺一不可：

- **Harness 底座而非照抄**：复用成熟 Agent 框架的工程能力（Agent Loop、工具注册、多 Agent 编排、插件/连接器生态、沙箱与权限模型），但**不照搬其产品形态、不继承其业务方向**。项目有自己的业务方向，Harness 只是“发动机”，不是“整车”。
- **微服务架构**：业务逻辑按限界上下文拆分，服务间通过明确定义的 API 通信，独立开发、独立部署、独立生命周期。
- **本地优先 + 云原生就绪**：前期纯本地开发、无 CI/CD、无云环境；但所有框架选型和代码组织必须**提前满足未来迁移到成熟云原生体系**的要求。

## 二、架构原则（不可妥协）

### 2.1 必须是微服务，且不能是分布式单体

这是本项目最容易走偏的地方，必须反复强调。

**微服务的判定标准**（同时满足才算数）：

| 维度 | 必须满足 | 反例（分布式单体特征） |
|---|---|---|
| 服务边界 | 按业务能力/限界上下文拆分，边界清晰 | 按技术层拆（controller 服务、service 服务） |
| 通信 | 仅通过明确定义的 API（REST / gRPC / 消息）交互 | 服务间直接读对方数据库、共享内存、共享代码库内部模块 |
| 数据 | 每个服务独占自己的数据存储 | 多个服务共享同一个数据库/schema |
| 部署 | 任一服务可独立构建、独立部署、独立升级 | 必须一起部署才能工作 |
| 故障 | 单个服务故障不导致全局瘫痪（有降级/隔离） | 一个服务挂掉整条链路全挂 |

**硬性禁令**：

- ❌ 禁止共享数据库。每个微服务拥有独立的数据存储（可以是同一台机器上的不同 schema/实例，但逻辑上独占）。
- ❌ 禁止跨服务直接调用内部实现（import 对方代码、直连对方端口绕过 API 网关/契约）。
- ❌ 禁止“为了省事”把多个服务塞进一个进程部署。本地开发可以同机多进程，但**必须多进程**。
- ❌ 禁止服务间强同步耦合导致必须同时上线。

### 2.2 云原生就绪 ≠ 现在就上云

**前期不引入**：Kubernetes、服务网格、云厂商托管服务、CI/CD 流水线、集中式可观测性平台。

**但必须提前满足的“就绪”条件**（这些是框架选型的硬约束）：

1. **容器化友好**：每个服务能独立打成一个 OCI 镜像（Dockerfile 从第一天就要有，哪怕本地用 Docker Compose 跑）。
2. **配置外置**：所有环境相关配置（端口、数据库地址、密钥）通过环境变量或配置文件注入，**禁止硬编码**。12-Factor App 原则中的配置分离必须遵守。
3. **无状态优先**：服务实例本身不持有会话状态；状态放外部存储（数据库/缓存/对象存储）。这样未来才能水平扩容。
4. **健康检查端点**：每个服务必须暴露 `/health`（liveness）和 `/ready`（readiness）端点，为未来 K8s 探针做准备。
5. **日志结构化**：输出 JSON 格式结构化日志到 stdout，不写本地文件。未来才能被云原生日志采集。
6. **服务发现抽象**：本地用 `localhost:端口` 或本地注册中心（Nacos/Eureka 本地实例），但**服务寻址必须通过配置/注册中心抽象**，不能把 IP 硬编码进代码。未来切换 K8s Service 时只改配置。
7. **优雅关闭**：服务收到 SIGTERM 后能完成在途请求再退出。这是容器编排的基本要求。

### 2.3 本地开发形态

- **编排工具**：Docker Compose 作为本地微服务系统的标准启动方式。一个 `docker-compose.yml` 拉起所有服务 + 中间件（数据库、消息队列、注册中心）。
- **开发模式**：每个服务支持“本地进程直跑 + 热重载”的开发模式（不每次都走容器构建），容器模式用于集成验证。
- **服务发现**：本地可用轻量注册中心（Nacos/Eureka 本地实例）或 Compose 内置 DNS；对外部依赖可用 Mock/Stub 隔离。
- **禁止**：为了本地方便而引入只在本地生效的硬编码逻辑（如 `if (env === 'local') { 直连某服务 }`）。本地与生产的差异只能通过配置体现。

## 三、Harness 层：改造策略（借底蕴，不照抄）

### 3.1 定位

Harness 层是本项目的 **Agent 运行时基座**，负责：Agent Loop、工具调用与注册、多 Agent 编排、上下文管理、会话、权限/Hooks、插件与连接器加载、沙箱执行。

**它不是**：产品 UI、业务工作流、业务数据模型、最终用户交互形态。

### 3.2 底座选型：DeepSeek Harness（dsh）

选定理由：

- **MIT 开源、官方维护**，工程底蕴成熟。
- **“一切皆插件”架构**：模型适配器、工具、会话、沙箱、甚至 Agent 主循环均可替换/扩展，天然适合业务化改造。
- **model-agnostic**：可接 Claude / GPT / DeepSeek 等任意 LLM 后端，不被单一模型商绑定。
- **原生多 Agent 编排**：内置 `subagent`（独立上下文）、`subagent_fork`（继承历史）、`workflow`（脚本化并行编排）、`ralph`（防死循环迭代），满足“像 Claude Code 一样自动分配多 Agent”的需求。
- **丰富的连接器生态**：IM 平台（飞书/微信/钉钉/Slack/Telegram 等）、MCP 连接器（可接任意 MCP 工具与服务）、浏览器操控（`dsh-chrome-control` / `dsh-builtin-browser` / CDP 驱动）、本机文件与 Shell（工作区沙箱模型）。
- **多语言接入**：Python SDK（`deepseek-harness-sdk`）为主；任意语言可走 CLI headless 模式（stdio + stream-json）。

**风险与对策**：

- dsh 处于 **Developer Preview**，官方明确会有 breaking changes → **锁定 SDK/依赖版本**，封装适配层隔离上游变化。
- 不直接在产品代码中散落调用 dsh API → **建立 Harness Adapter 层**（见 3.3）。

### 3.3 改造原则：Adapter 隔离 + 选择性继承

```
┌─────────────────────────────────────────────┐
│              业务服务（微服务群）              │
│   业务工作流 / 业务数据 / 产品交互 / 领域逻辑   │
└──────────────────┬──────────────────────────┘
                   │ 只通过 Harness Adapter 契约调用
┌──────────────────▼──────────────────────────┐
│           Harness Adapter 层（自研）          │
│  统一接口：runTask / spawnSubAgent /          │
│  registerTool / loadConnector / getSession … │
│  负责：版本隔离、能力裁剪、业务注入、审计埋点   │
└──────────────────┬──────────────────────────┘
                   │ 适配
┌──────────────────▼──────────────────────────┐
│        DeepSeek Harness（上游底座）           │
│  Agent Loop / 工具注册 / 多 Agent / 沙箱 /    │
│  插件加载 / 连接器 / 会话                     │
└─────────────────────────────────────────────┘
```

**必须遵守的改造纪律**：

1. **Adapter 层是唯一接触 dsh 的地方**。业务服务不直接 import dsh SDK 或调用其 CLI。上游升级时只改 Adapter。
2. **能力按需裁剪**：dsh 的插件/连接器生态非常庞大（社区超万级），**只启用业务需要的**，不默认全量加载。减少攻击面与维护负担。
3. **业务注入而非业务侵入**：业务逻辑通过“注册自定义工具 / 自定义插件 / 工作流定义”注入 Harness，**不修改 dsh 内核源码**。若必须改内核，以 fork + patch 方式并记录在案，且优先推动 upstream。
4. **Harness 层本身也作为微服务**：建议将 Harness 运行时封装为一个（或一组）独立服务，对外暴露任务提交/状态查询/事件流 API。业务服务通过 API 调用它，而不是在每个业务服务内嵌一份 Harness。这样 Harness 可独立扩缩容、独立升级，符合微服务原则。
5. **不继承 dsh 的产品形态**：dsh 自带的 Web UI、聊天交互、默认工作区模型等，仅作参考/调试用，**不作为产品交付形态**。产品形态由本项目自主定义。

### 3.4 桌面端与浏览器/本机操控

- **桌面框架选型**：**Electron 优先**（团队有网页开发经验，迁移成本最低，生态成熟）。Tauri 作为备选（体积小但需 Rust）。
- **开发模式认知**：开发期桌面窗口指向本地 Vite 开发服务器，**前端热重载、无需每次打包**；仅发布时执行打包。不要为“打包下载”焦虑。
- **浏览器操控**：通过 dsh 的浏览器插件能力（真实浏览器驱动 / CDP / Playwright）实现，经 Adapter 暴露为业务工具。
- **本机操控**：沿用 dsh 的**工作区沙箱模型**——Agent 的文件/Shell 操作严格限制在指定工作区目录内，危险操作经 Hooks 审批门。这是安全边界，不得为便利而绕过。

## 四、技术选型原则（给下一个 AI 的判断依据）

当面临选型或实现决策时，按以下优先级判断：

1. **是否破坏微服务边界？** 破坏则否决。
2. **是否引入“只能在本地跑”的硬编码？** 是则否决，改为配置化。
3. **是否让未来云原生迁移更难？** 是则否决（例如：引入强绑定某云厂商的 SDK 而不做抽象层）。
4. **是否绕过 Harness Adapter 直连 dsh？** 是则否决。
5. **是否把 Harness 的业务能力与业务服务耦合在一个进程？** 是则重新设计。
6. **是否为了“快速跑通”而共享数据库/共享代码？** 是则否决，这是分布式单体的起点。
7. **上游 dsh 的 breaking change 是否会波及业务代码？** 会则说明 Adapter 隔离不彻底，需补强。

## 五、开发工作流（当前阶段）

| 环节 | 当前做法 | 未来演进（不现在做） |
|---|---|---|
| 代码组织 | Monorepo（推荐），按服务分目录，每个服务独立 Dockerfile | 拆仓或保持 Monorepo + 独立流水线 |
| 本地运行 | Docker Compose 拉起全套 + 单服务热重载开发模式 | — |
| 构建 | 每服务独立构建，产出 OCI 镜像 | CI 自动构建推送镜像仓库 |
| 测试 | 单服务单测 + Compose 集成测试；外部依赖 Mock | 契约测试、混沌测试 |
| 部署 | 本地 Compose / 单机多进程 | K8s / 云托管 |
| 配置 | 环境变量 + 配置文件，禁止硬编码 | ConfigMap / Secret |
| 日志 | 结构化 JSON → stdout | 云原生日志采集 |
| 可观测性 | 基础 health/ready 端点 + 本地日志 | Metrics / Tracing / 集中平台 |
| CI/CD | **无**（明确不做） | 后期引入 |

## 六、明确的反模式清单（看到即纠正）

- ❌ 分布式单体：服务间共享数据库、必须同时部署、跨服务直接 import。
- ❌ 在业务服务里直接 `import deepseek_harness` 或调 dsh CLI。
- ❌ 把 Harness 运行时嵌进每个业务服务进程。
- ❌ 硬编码 localhost / IP / 端口 / 密钥。
- ❌ 引入只在本地生效的条件分支逻辑。
- ❌ 为了“先跑通”而让多个服务共用一个数据库 schema。
- ❌ 全量加载 dsh 社区插件，不做裁剪。
- ❌ 修改 dsh 内核源码而不走 fork+patch 记录流程。
- ❌ 把 dsh 自带 Web UI 当作产品 UI 直接交付。
- ❌ 开发期反复打包桌面应用（应使用开发模式热重载）。
- ❌ 绕过工作区沙箱让 Agent 任意操控本机文件系统。

## 七、阶段性路线（供对齐预期，不约束细节）

- **阶段一（当前）**：本地微服务骨架 + Harness Adapter 层 + dsh 集成跑通 + 桌面端开发模式界面。目标：验证“业务服务 → Adapter → dsh → 多 Agent 执行”全链路。
- **阶段二**：业务服务补全、服务边界固化、Compose 集成测试完善、浏览器/本机操控能力经 Adapter 暴露。
- **阶段三**：容器镜像标准化、health/ready 完善、配置外置审计、日志结构化。
- **阶段四（未来）**：引入 CI/CD、迁移 K8s、接入可观测性平台。**此阶段不改架构，只补运维交付能力。**

## 八、给下一个 AI 的行为准则

1. **先读本文档再动手**。任何实现决策与本文冲突时，以本文为准，并明确指出冲突点。
2. **不确定是否破坏微服务边界时，停下来问**，不要“先写了再说”。
3. **接触 dsh 的代码一律放在 Adapter 层**，业务代码只依赖 Adapter 暴露的接口。
4. **新增服务前先确认限界上下文**，不要在已有服务里堆不相关逻辑。
5. **任何“本地特判”都要标记为待偿还技术债**，并给出配置化方案。
6. **不要主动引入 CI/CD、K8s、云服务**，除非用户明确进入阶段四。
7. **不要照搬 dsh 的产品形态或业务方向**，只借用其工程能力。
