# ADR 0005：任务的进门与出门（5.3）

- 状态：已采纳（2026-10-22，用户确认第 9 节的三项）
- 依据：ADR 0003 第 3 节（五道门）、ADR 0004（工作流控制面）、用户 2026-10-22 的决定
- 范围：conversation、task、harness、model-gateway（不新增服务）

## 背景

5.2 做完后，task 已经能接收一份工作流方案并跑完。5.3 要补齐两头：

- **进门**：用户在私聊里说出需求 → 认出这是任务 → 用普通话把需求问清楚 → 给出任务单 → 用户确认 → AI 团队排出工作流 → 开跑。
- **出门**：工作流跑完 → 对照任务单整体验收 → 把成果交回私聊。

界面（任务卡、问题卡、任务单卡、「正在搭建工作流」）在 5.5 做；5.3 把这些卡片背后的数据和接口做好，用接口测试和真实模型验收。

## 决定

### 1. 一条任务在私聊里的样子

```
用户：帮我给小木屋民宿写个官网首页
  └ Jev 判断「这是在交代一件要交付成果的事」 → 进入接需求
AI（问题卡）：几个选择题，每题有默认项和「你看着办」
用户：选好答案（或点「直接开始」，全部用默认）
AI（任务单卡）：要交付什么、怎么算做好、风格与限制、AI 自己定的事
用户：确认（或在对话里说「风格改成…」，AI 改出新的任务单，只留最新一份）
  └ task 建任务，状态「规划中」；规划员（一次 harness 运行）排出工作流 → 规划门检查 → 算出预估 → 开跑
AI（任务卡）：显示进度、花费；需要处理时提醒
  └ 工作流跑完 → 整体验收 → 交付
AI（交付消息）：做了什么、成果文件、没完全满足的地方（如果有）
```

### 2. 认出任务

- 私聊里每条用户消息先问一次 Jev（Noul：「是否在交代一件要交付成果的事」），约百万分之几美元。
- 概率 ≥ 0.7：进入接需求。0.4–0.7：照常聊天，回复下面附一个「当成任务来做」的按钮。< 0.4：照常聊天。
- 界面上也可以直接点「发任务」，不经过判断。
- 进入接需求后，用户说「不用了 / 只是聊聊」可以退出（问题卡上有「不是任务」按钮）。

### 3. 接需求（问题卡和任务单）——由私聊里的这个 AI 来做

- 谁来问：就是用户正在聊的这个 AI（比如 Claude）。它「只负责读懂需求」，不决定团队和工具。
- 怎么做：conversation 直接经 model-gateway 调这个 AI 的模型，要求它按固定 JSON 回答：要么给出问题，要么给出任务单。解析失败就带着错误再要一次；还不行就换默认模型（DeepSeek）来做。
- 这里**不走 harness**（和 ADR 0003「所有需要想的环节都是一次 harness 运行」不同）：这是聊天里的一来一回，起一个容器要多等几秒；它也不需要读写文件。用户上传的素材（5.5）只把文件名和大小告诉它。
- 问题的规矩（写进它的说明里，也由代码检查）：
  - 只问普通人听得懂的需求问题（给谁看、要什么风格、要几个版本），技术问题自己定；
  - 每题是选择题，2–5 个选项，必须标出默认项，并自带「你看着办」；
  - 最多问 **3 轮**、每轮最多 **4 题**（用户定）；用户可以随时点「直接开始」，没答的全按默认。
- 任务单的内容：
  - 标题；
  - 要交付的东西（每样：名称、形式，如「首页文案，Markdown」）；
  - 怎么算做好（普通话，最多 8 条；之后变成节点关卡和整体验收的验收点）；
  - 风格与限制；
  - 用户自己设的花费上限（可选）；
  - AI 自己定的事（技术假设，让用户知道，不用确认）；
  - 素材（用户上传的文件）。

### 4. 规划（规划员 + 规划门）

- 用户确认任务单后，conversation 调 task 的 `POST /internal/tasks`（新形状：带任务单，不带方案）。task 建任务，状态「规划中」，开一次规划员运行（harness，默认 DeepSeek）。
- 规划员拿到：任务单、可用的模型目录（agent 服务里接好的模型）、节点类型和规矩。它把方案写进 `out/plan.json`：节点（干活 / 讨论，带验收点）、连线，以及「每样交付物由哪个节点负责」。
- 规划门（代码检查，ADR 0003 第 3 节②）：
  - 格式对、节点名不重复、没有环、没有断开的线（复用 5.2 的校验）；
  - 用到的模型都在目录里且已接入；
  - 任务单上每样交付物都有节点负责；节点数在上限内（先定 12 个）；
  - 不过：带着问题接着原会话让规划员改一次；还不过，任务进入「需要处理」（重新规划 / 取消）。
- 预估花费由代码算，不让 AI 估：按节点数、讨论轮数和每类运行的经验单价算（5.2 实测：干活约 $0.002–0.003/次，讨论每次发言或汇总约 $0.003，关卡忽略不计）。以后用真实记账数据校准。
- 花费上限：任务单里用户自己设了上限就用它，否则用预估 × 3（ADR 0004 第 8 节）。预估已经超过用户设的上限时，不开跑，进入「需要处理」：按预估继续 / 取消。
- 规划通过就立即开跑，用户不审方案；任务卡上显示「预计花费约 $x」。

### 5. 整体验收（出门）

- 工作流全部完成后，用和节点出口同一套轻量关卡检查**负责交付物的节点**的产出：规则检查（交付物文件在、不是空的）+ Jev 逐条判断任务单里「怎么算做好」。
- 通过：交付。
- 没通过：照样交付，交付消息里写明哪些地方没满足，由用户决定要不要发起修改（用户定；已完成的节点不能改，修改 = 新的工作流）。

### 6. 交付

- task 经发件箱发 `task.task.delivered`（以及 `task.task.planned`、`task.task.attention`、`task.task.failed`、`task.task.cancelled`），conversation 持久消费：
  - 更新私聊里的任务卡（状态、花费、需要处理的原因）；
  - 交付时由私聊里的 AI 发一条交付消息：做了什么、成果文件清单、没完全满足的地方。
- 成果文件的下载：新增 `GET /v1/tasks/:id/files/:nodeId/*`（task 转给 harness 读对象存储），交付消息和 5.5 的画布都用它。5.5 再把成果登记进画布。

### 7. 私聊消息的形状

`messages` 表加 `kind`（`text` / `questions` / `sheet` / `task` / `delivery`）和 `data`（JSON）。问题卡记下用户的回答；任务单卡记下是否已确认、对应哪个任务。老消息都是 `text`。

### 8. 接口（经 gateway）

| 接口 | 作用 |
|---|---|
| `POST /v1/conversations/:id/messages` | 照旧；多一个可选 `asTask: true`（点「发任务」） |
| `POST /v1/conversations/:id/intake/answers` | 回答问题卡（可以只答一部分）；`skip: true` = 直接开始 |
| `POST /v1/conversations/:id/intake/cancel` | 不是任务 / 不做了 |
| `POST /v1/conversations/:id/intake/confirm` | 确认任务单 → 建任务 |
| `GET /v1/tasks/:id/files/:nodeId/*` | 下载成果文件 |

## 用户的决定（2026-10-22）

1. 整体验收没通过：直接交付并写明哪里没满足，不自动修正。
2. 追问上限：最多 3 轮、每轮最多 4 题，随时可以「直接开始」。
3. 接需求不走 harness：同意（第 3 节）。

## 实现时定下的细节（5.3）

- 消息类型共六种：`text` / `questions` / `sheet` / `task` / `delivery` / `notice`。交付消息和提醒由 task 的事件触发，按事件 ID 只发一条（`messages` 上的唯一索引）。
- 接需求的状态单独放一张表 `intakes`（在问 / 等确认 / 已确认 / 不做了），一个会话同时只有一个进行中的。接需求期间用户在对话里说的话，先由 Jev 判断是不是在说这件任务（2026-11-05 用户：上一条是任务，后面的话不能一律算任务）：是（或判断失败）就当作补充或修改意见交给 AI，AI 判断用户不想做了就回答 cancel；交代了另一件新任务，就把还没确认的这件收起来（回一句「上一件还没确认的任务先放下了」），按新需求开始整理；都不是就照常聊天，不附「当成任务来做」，任务卡片留着可以接着点。同日修复：素材解析里的图片原图（base64）不再写进接需求的提示词和记录，之前一张 2.4 MB 的图会让请求超过模型上下文上限。同日第二轮（用户试用：外卖骑手参考图被说成马车）：①开始接需求时，上下文只取上一个任务之后的聊天——上一个任务的原话、修改意见、卡片和交付消息以及它们带的文件都不再算进来（原来取最近 8 条文字消息，把旧马车任务的原话和两张批注截图带成了素材）；②问需求的 AI 看不了图，图片素材在材料解析后先交给 `image.inspect` 描述一遍（每张图一次，失败只说是图片），描述写进素材说明并注明不是用户原话；③问题卡每题加「自己写」，答案存成 `custom:原话`（1–300 字），AI 按原话理解，没写进任务单时由系统按原话补一条要求，来源 optionId 为 custom。
- 私聊 AI 每一步只调用一次模型，不重试、不换模型重来（2026-11-04 起，见下文同日小节）；当前地区用不了的模型事先改用 `INTAKE_FALLBACK_MODEL`（默认 DeepSeek）。网络或额度错误保留原话和答案，允许继续整理，不要求用户重述。
- 认出任务的阈值：`TASK_DETECT_HIGH`（0.7）、`TASK_DETECT_LOW`（0.4）；Jev 出错时当成不是任务，照常聊天。
- 规划员拿到的模型目录来自 agent 新增的 `GET /internal/models/catalog`（只列已接入的）。方案最多 `MAX_PLAN_NODES`（12）个节点，规划员最多跑 `MAX_PLAN_ATTEMPTS`（2）次。
- 预估单价：`ESTIMATE_WORK_RUN_MICRO` 和 `ESTIMATE_SPEECH_RUN_MICRO`（都是 $0.003），总数再加两成。
- 任务多了两个状态：「规划中」（`planning`）和「验收中」（`accepting`）；这两个状态下不能改工作流。「需要处理」多了两个原因：`plan_failed`（重新规划 / 取消）和 `over_estimate`（照做 / 取消）。
- 整体验收把负责交付物的节点交出的东西一起交给关卡（每个节点标上交付物名）；节点没交出文件就直接记为没满足。
- task 每次状态或「需要处理」的原因变化，都在同一个事务里往发件箱写 `task.task.status_changed`。conversation 在完成时发交付消息，在需要处理或失败时发提醒；规划中、运行中、已取消不发。
- 交付消息按模板生成，不再调一次模型：省钱，内容也确定。
- 下载成果：task `GET /v1/tasks/:id/files/:nodeId/*` 转给 harness 新增的 `GET /internal/runs/:runId/files/*`；只能下载节点产出清单里有的文件。

## 2026-10-22 用户试用后的修正

用户在 Windows 上用真实模型试了一次（「官网首页首屏：文案 + 效果图」）。规划员给效果图节点选了 GPT，给讨论里的一位参与者选了 Gemini，这两个模型在用户网络所在的地区都用不了，节点各重试 3 次后失败。修正：

- model-gateway 新增 `GET /internal/v1/models/unavailable`：按调用记录，列出最近一次聊天调用因地区限制被拒、之后没再成功过的模型。规划员的模型目录里去掉这些。部署到海外后没有被拒的记录，就不会排除任何模型，不需要配置。
- 节点运行碰上「地区不可用」：重试没用，直接换成默认模型（DeepSeek）接着做，不算一次重做，并在节点上留提醒。讨论里只换那位参与者的模型。默认模型也用不了时，照常按失败处理。

## 后果

### 2026-11-02 私聊交互要求、实施与真实任务跟踪

#### 同日实施设计（真实任务停止后）

- 复用 messages.data，文字用户消息记录 intent=chat/task，普通 AI 回复记录 replyTo；任务来源记录 intakeId，停止结果记录 stopped。不新增表、依赖或消息版本副本。旧任务来源按 intakes 保存的原话和用户补充恢复保护，重复文本保守保护；新消息用显式来源，不凭相邻卡片猜测任务性质。
- DELETE messages/:messageId 删除普通用户消息及对应普通回复；POST messages/:messageId/reply（可选 content）修改/重生成本轮；POST messages/:messageId/stop 停止当前普通回复。全部先验证会话归属和消息性质。编辑与重生成只替换本轮，后续消息保留；生成只使用本轮之前的历史。删除和替换物理移除旧正文/回复，不保留隐式版本；未确认 intake 的上下文快照同步移除关联旧文本，已派发任务不追溯修改。
- 普通消息修改共用数据库 advisory lock，发送、删除和替换互斥；停止绕过长调用锁，通过持久停止标记和本地 AbortController 取消上游，跨实例轮询标记，防止旧流迟到覆盖。intake/start 同样参与消息锁；任务原话、补充和修订原话从识别为任务起锁定。停止不调用 task/harness。
- 长文气泡给短预览，全文用原生 dialog，编辑也在 dialog 中完成，均复用现有令牌和交互方式。
- Harness 只承认 completed 为成功结束；max-tokens、取消及未知结束原因均失败，且未收到结束通知不能成功。保留既有关卡返工策略，重复的缺文件说明去重。不重写已有失败任务或账单，不付费重跑。

用户最初明确要求先保护正在运行的真实任务，当时只记录以下要求、设计边界与只读证据。任务停止后用户授权实施，完成情况与耗时复盘见本节末尾。

1. 长聊天/长任务正文在聊天流中显示短预览，查看全文用独立小窗口（可滚动、关闭与复制），不在聊天流中就地展开。
2. 作为任务提交的用户消息须有明确任务标识，发布后不允许修改、删除或重新生成。服务端也须强制限制；不能只隐藏按钮。需保存可靠的任务来源关联，不能仅凭内容长短、文案或相邻消息猜测。
3. 普通聊天提供删除、编辑和重新生成。删除必须连同对应 AI 回答一起移除，并从未来模型上下文排除；编辑/重新生成替换对应回复，不把旧文本、旧回复或并发迟到结果偷偷留进上下文。实现前明确后续对话处理及任务消息边界，不追溯修改已派发任务的输入、费用或工作流。
4. 普通聊天的回复/思考可停止。停止应取消当前聊天调用，保存已经收到的部分并标明停止；不能只是把动画关掉、让上游继续扣费。后续是否继续生成由用户主动触发。停止聊天绝不能调用 task/harness 的暂停、取消或停止接口；已派发的后台任务继续运行。
5. 节点显示的完成状态需区别运行正常结束、输出被截断、检查不通过及真正交付。不得把 max-tokens 等非正常结束直接当成功，也不能为消掉提醒放宽必需文件检查。现有“一次关卡返工后仍不通过就留提醒继续”的产品决定保持，运行协议错误和关卡策略分别处理。

受影响模块预期为 Web 的消息气泡/全文弹窗/输入框、conversation 的消息来源/轮次关联及操作权限、model-gateway 的普通聊天取消传播、harness adapter 的结束原因解释；task 的既有关卡策略不在本次擅改。优先复用既有对话、消息、弹窗与计量链路；数据及 API 在真正实施前冻结，不预建表或安装依赖。

### 2026-11-02 任务单生成与失败恢复修复
