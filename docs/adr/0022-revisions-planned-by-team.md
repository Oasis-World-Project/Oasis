# ADR 0022：修改交给 AI 团队规划，工作流分版本，先确认再跑

状态：已采纳（用户 2026-11-08 决定）。取代 ADR 0012 里 2026-11-05 的「不重新规划、交付节点接着原会话改、下游跟着更新」。

## 1. 起因

雨夜便利店任务：用户在网页成果上批注「太暗，加光」。系统把所有负责交付物的节点（建模节点交预览图、网页节点交网页）连同下游一起重跑，修改交给了建模节点，它接着 30 分钟的长会话改，5 分钟花了 $5.05（比第一次从零建模还贵），网页节点还在后面等着重做。按理只要网页节点加几盏灯。另外修改一开始，节点状态全被重置，任务卡显示「0/2 完成」，看不出这是在修改，之前的工作流也看不到了。

## 2. 决定

1. **修改先交给规划员。** 用户发出修改意见（文字、批注、参数）后，规划员拿到：原任务和任务单、修改意见、意见针对的节点（批注和参数所在成果的节点，ADR 0021 §7 的 `nodeIds`）、上一版工作流（每个节点的模型、要做的事、产出文件、花费、用时、状态）。它自己决定怎么改，写成 `out/plan.json`：
   - `{"key": "...", "reuse": "<旧节点>"}`：沿用，不重跑，产出原样交给下游；
   - 完整节点 + `"from": "<旧节点>", "mode": "continue"`：接着原会话改（会话越长越贵，花费和用时都给规划员看）；
   - 完整节点 + `"from": "<旧节点>"`（`mode` 缺省为 `fresh`）：重新开会话做，上一版这个节点交出的文件放进 `in/_previous/`；
   - 完整节点、没有 `from`：新节点；旧节点没出现在方案里就删掉；
   - `summary`：一两句话告诉用户打算怎么改。
   规划门照常检查（模型、工具、交付物）；另外检查：沿用的节点要有上一版产出、它的上游也都是沿用；接着原会话要用原来的模型、原来是干活节点；同一个旧节点只能被引用一次。
2. **先确认再跑。** 方案过了规划门，任务进入「需要处理」（原因 `revision_plan`），显示规划员的说明、每个节点怎么处理（沿用 / 接着改 / 重新做 / 新增 / 删除）和预估花费（只算要跑的节点）。用户点「确认修改」才开跑，点「不改了」回到修改前的状态，成果不变。
3. **工作流分版本。** 确认时先把当前工作流（节点、连线、交付物分工、花费）冻结成一个版本存进 `workflow_versions`，再按方案改当前工作流：被沿用或带 `from` 的节点保留原来的 ID（成果、同步路径、运行记录都接得上），新节点新 ID。工作流页底部可以切换「第 1 版 / 第 2 版」，旧版只读，节点的运行记录只显示那一版冻结前的。被删掉的节点留在表里（`nodes.retired_version`），不真删，运行记录还在。
4. **「修改中」标签。** 从发出修改到新版交付（或取消），任务卡和工作流页都标「修改中」，进度按新版的节点算。
5. **画布跟着最新一版。** 改过的任务再次交付时，内容变了的成果原地换新（链接不变）；新版不再交付的旧成果从画布删掉（ADR 0012 §15 真删除）。

## 3. 状态和接口

- `tasks.version`（当前第几版，默认 1）、`tasks.revision`（进行中的修改：目标版本、意见、针对的节点、修改前的状态、通过规划门的方案、预估、说明）。
- `nodes.retired_version`：在第几版被删掉；当前工作流不显示，旧版和运行记录还能看。
- `TaskBody` 加 `version`、`versions`（冻结的旧版列表）、`revision`（`stage: planning | confirm`、说明、预估、每个节点的处理）、`revising`（修改中，任务列表的 `TaskSummary.revising` 同一个规则：有进行中的修改，或新版还没结束，中途停下也算）。
- 确认沿用「需要处理」的选择：`POST /v1/tasks/:id/decision`，`continue` 是确认修改，`cancel` 是不改了；规划中点「不改了」走 `POST /v1/tasks/:id/cancel`。有进行中的修改时，这两个取消都只撤掉这次修改，不取消任务。
- `GET /v1/tasks/:id/versions/:version` 取冻结的旧版。
- 规划员的提示词和规划门在 `services/task/src/service/revision-planner.ts`；接着改的节点照旧走 `config.revision`（修改意见 + 规划员给这一步的安排），重新做的节点带 `config.previousRunId`，上一版产出作为输入放进 `in/_previous/`。
- 修改中途停下（`stopped`）的任务也能重新发修改。

## 4. 已知限制

- 看旧版时，节点产出的预览和下载仍按节点现在的产出取：节点在新版重做过的，看到的是新版文件。要看旧文件得按运行取，以后再做。
- 2026-11-08 之前按旧流程发起、还没结束的修改（节点上留着 `config.revision`）：重新发修改时，沿用的节点会清掉这些残留。

## 5. 验证

- task 服务测试：发修改 → 规划员拿到意见、针对的节点、上一版工作流 → 方案过规划门后停在待确认，不跑任何节点 → 确认后冻结第 1 版，接着改的节点接原会话，重新做的节点拿到 `_previous` 输入 → 交付后版本 2；沿用 + 新增 + 删除；规划门挡住上游要重做的沿用并退回规划员；规划中、待确认时不改了回到修改前的状态。
- 画布测试：新版不再交付的旧成果被删掉，新版什么也没交出时保留。
- 前端测试：待确认的方案在工作流和私聊任务卡上显示、确认；规划中显示横幅和「不改了」；切到旧版只读。
