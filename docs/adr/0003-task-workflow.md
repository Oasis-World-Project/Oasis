# ADR 0003：任务与工作流（第 5 阶段）

- 状态：草案（2026-10-22），待用户确认后改为「已采纳」
- 依据：`docs/engineering/项目工程方向.md`、ADR 0001、ADR 0002、用户 2026-10-22 的决定、14 个业务场景说明、5.0 dsh 技术验证
- 范围：task、harness、model-gateway、canvas、agent、billing、conversation、gateway、Web、desktop

## 背景

第 5 阶段要让用户在私聊里提出一个需求，由后台的 AI 团队搭出一条为它定制的可视化工作流，执行完把成果放进画布。用户给出了 14 个业务场景（文档、音频、视频、网页、小游戏、3D、渲染、图片、UI 测试、合成数据、数字人、营销、深度研究；知识库场景已移出本阶段），要求本阶段全部支持，工作流必须完整，不能只做单节点。

## 决定

### 1. 产品规则（用户确认）

| 规则 | 内容 |
|---|---|
| 入口 | 先在私聊里发任务。聊天的 AI 只负责读懂需求、交给后台团队；节点用什么模型、什么工具由工作流决定，和聊天的 AI 无关；同一个模型可以在多个节点重复使用 |
| 追问时机 | 需求问题全部在工作流搭建前问完，只问普通人听得懂的需求问题；技术问题 AI 自己定 |
| 任务单 | 问完后给用户看任务单，用户确认后系统开始搭建定制的可视化工作流（需要一点时间）；团队方案不需要用户先审 |
| 节点关系 | 四种：串行、并行、讨论、互审 |
| 运行中 | 节点里的 AI 不会主动问用户。用户可以对运行中或等待中的节点追问、提修改要求，也可以自己修改等待中的节点 |
| 已完成节点 | 不能追问、不能修改、不能删除 |
| 修改不传递 | 用户对某个节点的修改只改这一个节点，系统不会自动更新后面的节点。即使修改和原需求不一致，后面的节点也照样拿上一个节点的产出继续做，除非用户自己去后面的节点追问或修改 |
| 修改成果 | 工作流结束后，用户批注或直接让 AI 改，在用户看来就是重新生成一条工作流（内部可以复用或微调节点，用户看不到） |
| 旧版本 | 不保留，无法找回 |
| 预算 | 任务不设预算上限；用户在任务单里自己写了上限的，照办 |
| 防失控 | 节点重做或被打回超过上限，或实际花费超过预估 3 倍时，暂停并问用户 |
| 计费 | 模型、工具、算力（容器时长、GPU 时长、预览环境时长）都要算钱 |
| 本地文件 | 网页端上传文件；桌面端可以绑定一个本地文件夹，资料自动同步上去，成果自动同步回来；执行一律在服务端 |
| 工具 | 路径和工具由 AI 团队决策，不做写死的模板映射；原型里的工具都可替换；专业工具的接入由用户解决 |
| Jev | 作为工具参与工作流，也能被系统直接调用，本阶段接入 |

### 2. 服务职责

不新增服务。

| 服务 | 第 5 阶段的职责 |
|---|---|
| conversation | 接需求：在私聊里识别任务、展示问题卡和任务单、收确认、显示任务卡和交付消息 |
| task | 控制面：任务单、工作流图、节点状态机、调度、门禁、防失控、把用户追问转给对应节点 |
| harness | 执行面：dsh Adapter、定制的 dsh 组合、执行器（容器 / 云 GPU）、会话存档与恢复、预览环境、把 dsh 事件翻译成 Oasis 事件 |
| model-gateway | 所有模型和外部工具调用的唯一出口：工具调用格式、每次运行的临时 Key、外部工具适配、长任务、按单位计量 |
| agent | 模型与工具目录（工具可替换，规划只能从目录里选） |
| billing | 按 token、按单位（秒、张、首、个）和按算力时长计价扣费 |
| canvas | 成果：文件、版本、条目、审批、导出、上传、本地文件夹同步接口 |
| desktop | 绑定本地文件夹、双向同步（通过 preload 暴露明确接口） |

所有需要「想」的环节（需求分析、规划、节点执行、验收）都是一次 harness 运行，只是角色不同。这样计费、审计、事件流只有一条路径。

### 3. 任务要过的五道门

| 门 | 产出 | 判定方式 |
|---|---|---|
| ① 需求澄清 | 任务单：交付物、普通话版验收标准、风格与限制、用户自设的上限、「AI 自行决定」的技术假设；待问问题（选择题，带默认项，可选「你看着办」） | 代码检查任务单字段完整、没有未答问题；通过后等用户确认 |
| ② 规划 | 工作流方案（我们定义的 JSON）：节点、关系、每个节点的角色、模型、工具、运行环境 | 代码检查：格式合法；除互审回路外没有环；模型和工具都在目录里且可用；任务单里每样交付物都有节点负责；算出预估花费 |
| ③ 执行 | 各节点的成果（中间产物存入画布） | 状态机 + 调度器 |
| ④ 验收 | 验收结论 + 需要修正的地方 | 独立的验收角色（不参与制作）对照验收标准检查，加机器检查（文件能打开、网页能运行、图片能解码等）；不通过退回负责的节点 |
| ⑤ 交付 | 画布里的最终成果、私聊里的交付消息、桌面端同步回本地文件夹 | 代码 |

### 4. 工作流模型

- 工作流是一张图：节点 + 依赖。
  - **串行**：上游产出交给下游。
  - **并行**：互不依赖的节点同时跑。
  - **讨论**：一组参与者来回 N 轮，由一名汇总者产出结论。
  - **互审**：审查者对照标准检查被审节点；不通过就带着修改意见让被审节点重做，最多 K 轮。
- 节点状态：等待 → 运行 → 待审（有互审时）→ 完成；另有暂停、失败、取消。
  - 只有通过互审（或没有审查者）才进入「完成」。因此「打回重做」发生在完成之前，不违反「已完成不可修改」。
  - 每次重做记一次 attempt，花费记在对应 attempt 上。
- 调度器只启动依赖都已完成的节点；并发数有上限。
- 服务崩溃后，从持久化的状态接着跑：已完成的节点不重跑，运行中的节点按失败重试处理。
- 用户的追问和修改只作用于他点开的那个节点（运行中或等待中），不向后传递，也不影响已完成的节点。
  - 对运行中的节点：消息直接插进它正在进行的 dsh 会话。
  - 对等待中的节点：记为它开始时的附加要求；用户也可以直接改它的目标。
- 节点的输入只认上游实际交付的产出，不会因为上游被改过而重新比对原需求。

### 5. dsh 的定制

- 精确锁定 `@deepseek-ai/dsh@0.2.1-rc.2`。只有 `services/harness/src/adapter/` 能接触它。
- 不用 dsh 自带的 profile，在 Adapter 里维护 Oasis 自己的组合，接入方式是 `--profile sdk`（JSON-RPC stdio）。
  - **拆掉**：DeepSeek 账号与官方模型、DeepSeek 网页搜索、goal、plan mode、jobs、schedule、自动起标题、ask_user / user-questions、审批、插件管理与插件市场、dsh 自带的 workflow 工具、遥测，以及其他用不上的。
  - **装上**：Oasis 模型路由（指向 model-gateway）、Oasis 工具（从目录生成，经 model-gateway 调用）。
  - 以后需要改 dsh 内核时，按 fork + patch 的方式记录在案。
- 容器内权限用 `danger-full-access`，隔离由容器负责。
- 会话存档：运行结束后，把 dsh 的会话存储打包存进对象存储。用途是互审打回后的重做（带着原来的上下文继续改）和服务崩溃后的恢复，不用于追问已完成的节点（已完成的节点不接受追问）。

### 6. 执行器与运行环境

- 执行器接口：启动、双向 stdio、拷入输入、拷出产出、停止、上报用量。实现有三种：
  - `docker`：harness 通过 Docker Engine API 起容器，本地挂载 docker.sock。
  - 以后的 `k8s-job`。
  - `cloud-gpu`：云上的无服务器 GPU，按秒计费。
- **GPU 策略**：厂商接口能做的一律调接口；没有接口的（如 Blender 渲染、视频重建 3D）用云 GPU；不依赖任何开发机或本地硬件。
- 运行环境是一组镜像，都叫 `oasis/harness-sandbox-<环境>:<dsh 版本>`：基础、文档、媒体（ffmpeg）、3D（Blender）、浏览器（Playwright、axe）。规划时为每个节点选一个。
- **网络**：
  - 容器只能访问 model-gateway，以及一个只放行软件包仓库（npm、PyPI 等）的出口代理。
  - 抓取网页、联网搜索也是工具，经 model-gateway 走，可计量、可审计。
  - 输入和产出由 harness 拷进拷出，容器不直接访问对象存储。
- **资源限制**：每个容器有 CPU、内存、时长上限；运行结束或取消时销毁容器、作废临时 Key。
- **预览环境**（网页、小游戏、UI 测试用）：运行结束后保留一个只供预览的容器，有存活时间。经 gateway 用独立域名嵌进画布。预览开着的时长也计费。

### 7. 模型与工具调用

- **临时 Key**：harness 向 model-gateway `POST /internal/run-keys` 申请，绑定付款人、任务、节点、运行和过期时间，只返回一次。库里存 sha256。运行结束就作废。
- **运行专用入口**：model-gateway 新开 `/run/v1/*`（OpenAI 兼容），用 Bearer 临时 Key 鉴权，只对沙箱网络开放，gateway 不转发。
- **chat completions 契约扩展**：
  - 消息支持 `tool_calls`、`role: tool`、`content: null` 和内容数组。
  - 请求支持 `tools`、`tool_choice`、`max_completion_tokens`。
  - 输出上限按模型目录来定，不再写死 32000。
- **外部工具**：统一的「调用工具」入口，按目录里的工具键路由到对应供应商。长任务的做法是先提交、再等结果，等待不占用节点的模型调用。
- **计量**：每次调用都记下任务、节点、运行；按实际花费 × 系数扣费。没有实际花费的，按目录里的单位价格。
- **Jev**：TypeSafe 的结构化决策模型（`typesafe/jev-1.14`，`~typesafe/jev-latest` 跟随最新版）。它不生成文字，只回答四类问题，并给出概率：
  - Choice：从几个选项里选一个。
  - Noul：某个条件是否成立。
  - Score：落在一个有序刻度的哪一档。
  - Box：在图里框出目标。

  它在 OpenRouter 的 Decisions API（`POST /api/alpha/decisions`）上，和聊天共用 OpenRouter Key，响应带 `usage.cost`；只按输入 token 收费，输出免费。model-gateway 给它开一个入口，内部服务用 `/internal/v1/decisions`，沙箱用 `/run/v1/decisions`，和聊天一样冻结、结算。用法：
  - 系统直接调用：判断私聊里的一句话是不是任务、规划时从目录里挑工具或模型、验收时逐条判断是否达标、互审时打分、以后群聊里决定谁接话（第 6 阶段）。
  - 节点里的 AI 当工具用：需要做选择、打分、框选时调用。
  - 概率阈值写进配置，换决策模型时要重新标定。

### 8. 计费

- 付款人是任务发起人（以后群里的任务是群主）。
- 三类扣费都走 billing 的「冻结 → 结算」：
  - 模型和工具：model-gateway 上报。
  - 算力：harness 按容器规格 × 时长、GPU 秒数、预览时长上报。
- 算力单价写进配置，默认按成本价。
- 任务卡实时显示已花费用；超过预估 3 倍时触发防失控暂停。

### 9. 事件（写进 `packages/contracts/src/events.ts`）

`task.task.*`（状态变化、需要用户确认、交付）· `task.node.ready` · `harness.run.started` / `progressed` / `finished` / `failed` · `canvas.artifact.updated` · `model-gateway.usage.recorded`（视需要）。

全部走 outbox + 持久消费者，消费者必须幂等。

## 已澄清（2026-10-22）

- 旧版本不保留，以用户的决定为准；`claude/canvas-module.md` 里的「旧版保留」作废。
- 已完成的节点既不能追问也不能修改；修改不向后传递（见第 1、4 节）。
- Jev 在 OpenRouter 上，共用 OpenRouter Key，不需要另外的接口文档或 Key。

## 后果

- harness 需要访问 Docker（本地挂载 docker.sock），权限较大，只在 harness 里出现。
- 沙箱镜像较大（dsh 依赖约 864 MB），按环境分镜像，并锁定版本。
- dsh 是预览版、没有协议版本协商：升级只改 Adapter；每次升级都要重跑 Adapter 的协议测试。
- 群聊、@、AI 设置与自带 Key 放在第 6 阶段，基线扫描放在第 7 阶段。
- 知识库场景移出第 5 阶段，作为以后的业务方向（接入个人知识库）。
