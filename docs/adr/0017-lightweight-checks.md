# ADR 0017：检查轻量化，节点自己验收

状态：用户 2026-11-07 确认方向（「我受不了每次手动跑一个任务半天跑不出来的情况了，就根据这个改」），已实施。取代 ADR 0004 §2 的 Jev 打分关卡（`GATE_MODEL`、`GATE_THRESHOLD` 配置已删除）。

## 1. 问题

2026-11-06 的「3D 低模复古马车」任务：做页面的节点 8 分钟交付，浏览器检查报页面错误，返工 27 分钟没停下来，花了 US$9.61 才被用户手动停掉。回看过去一周的检查问题，根子都在同一个结构上：

- **检查在事后、在外面、由另一套系统判。** 节点交付后，task 的关卡把产出、自然语言验收点和截图交给模型逐条打分（Jev、复核模型、看图模型），节点自己看不到也跑不了这些检查。
- **模型打分不稳。** 复核模型理由全写「placeholder」导致「未检查 13 项」；图片后缀和内容不符被看图检查判成签名无效、打回返工；规划员把自测写成强制检查导致未知阻断（ADR 0015 第七轮）。
- **反馈绕一大圈。** 浏览器报错只在关卡里有；节点返工时复现不了，只能猜。返工又是持续目标模式，节点改完说「完成」却没把目标标成完成，系统一轮轮叫它继续，关卡不再重查。
- **查两遍。** 节点关卡查过的东西，整体验收按任务单再逐条查一遍，于是又有「最多 5 条」「修改轮只查修改意见」这类补丁。`gate.ts` 长到 1130 行。

对照 dsh：检查是 agent 手里能运行的程序（测试、构建、门禁脚本），原始报错当场可见，改完马上能再跑；完成由 agent 拿着证据自己判断。

## 2. 决定

我们的产品是帮普通用户出成果，不是过审计的生产系统。检查只为一件事：别把明显坏掉的东西交给用户。用户接受：任务单上的「怎么算做好」不再由程序逐条核对，由节点自己对照、最后由用户看成果判断。

### 保留（便宜、确定，挡的是真问题）

1. 文件齐不齐：产出非空，方案写明的文件都在，数量和图片尺寸符合（按 harness 的文件解析报告，不调模型）；文件损坏（解析报错）算没满足。
2. 网页能不能打开：有 `oasis-app.json` 的成果在隔离浏览器里跑一遍，看页面错误和画面。
3. 音视频能不能播放：完整解码一遍。

### 删除

- 逐条验收点交给 Jev 打分、没结论再交给强模型复核；长文本先抽证据再判断。
- 截图描述、看图判断画面合不合要求（含修改素材的看图描述）。
- 整体验收再按任务单逐条查一遍：整体验收只核对交付文件是否齐全。
- 视频的黑屏、静音段、音画差提醒。
- task 的 `GATE_MODEL`、`GATE_EVIDENCE_MODEL`、`GATE_THRESHOLD`、`GATE_TEXT_MAX_CHARS`、`GATE_VISION_*` 配置。

### 节点自己验收

- 新工具 `app.check`：`oasis-tool app.check --dir out/site` 把节点当前的网页成果交给同一个隔离浏览器跑一遍（含 `oasis-test.json` 里的步骤），当场返回原始报错。关卡最后复跑的是同一套检查。
- 音视频用沙箱里的 ffprobe/ffmpeg 自己查时长、画幅、能否解码。
- 风格、像不像参考图这类主观要求，节点自己用 `image.inspect` 看，自己判断；系统不再另派模型打分。
- 方案里的 `checks` 留作节点自查清单（写进节点提示），关卡不再据此打分。

### 返工有界

- 关卡没满足时，返工改成单轮：节点在原会话里改一轮就结束运行，交回关卡复跑同一套检查；仍没满足就带着提醒往下走（最多自动改 1 次，ADR 0004 §2 不变）。返工不再进入持续目标模式，不会被一轮轮自动续跑。
- 干活节点第一次运行仍是持续目标（ADR 0015 不变）；它现在能自己跑检查，交付前就能把浏览器报错修掉。

## 3. 数据与契约

- 不新增迁移。`NodeConfig.gateChecks`、`TaskBody.acceptance.checks/notes` 不再写入新值；旧任务保留的值照常显示。Contract 计划：确认没有进行中的旧任务依赖它们后，删除 `NodeBody.gateChecks`、`acceptance.checks/notes`、`CheckResult` 的展示代码与配置字段。
- `repairChecks` 仍在用：整体验收发现交付文件不齐时，写给缺文件的交付节点（只给缺的那几个，不再让全部交付节点重做）。
- 用户提出的修改（ADR 0012）仍是一轮新工作，用持续目标；只有关卡和交付不齐触发的修复是单轮。
- 新增契约：model-gateway 工具 `app.check`（参数 `dir`）；harness `POST /internal/runs/:runId/application-check/live {payerId, taskId, dir}`：直接读这次运行中沙箱里的 `out/<dir>`，做与关卡相同的浏览器检查，不保存报告。不用把网页包从沙箱上传一遍，沙箱里的 oasis-tool 和镜像都不用改。
- `ApplicationCheckResult` 补导出类型。

## 4. 实施记录

2026-11-07：

- task：`gate.ts` 从 1130 行减到约 220 行，只剩文件解析、浏览器、音视频三类确定检查，不再调模型；`createGate` 只要 harness 和 logger。整体验收只查交付文件齐不齐，只让缺文件的交付节点补一次。删除 `filesForInspection`、`deliveryIntegrityChecks`、`revisionCheck` 和 `GATE_*` 配置。
- 关卡和交付不齐触发的修复是单轮（`goal: false`），修复提示要求用 `app.check`/ffprobe 自查、只修列出的问题；用户提出的修改仍是持续目标。
- 方案里的 `checks` 写进节点提示的【交付前自查】；规划员提示改成「自查清单」，负责交付物的节点也要列上要守的用户要求。
- harness：`preview-service` 拆出 `assemble`（按清单组装运行包）和 `browse`（隔离浏览器检查），关卡 `checkRun` 和自查 `checkLive` 共用；`run-service.liveFiles` 读运行中沙箱的目录。
- model-gateway：新增 `app.check` 工具，结果写成节点能照着改的话（原因、失败步骤、没检查到的地方）。
- 限制：同一用户同时只能有一个预览会话（含检查），用户正开着预览或另一个节点正在检查时，`app.check` 会返回「请先停止已有预览」，稍后重试即可。
