# ADR 0004：工作流控制面（5.2）

- 状态：已采纳（2026-10-22，用户确认第 1–5 点；第 11 节两处细节待确认）
- 依据：ADR 0003（产品规则、五道门、四种节点关系）、5.1 已落地的 harness 与 model-gateway、dsh 的门控设计
- 范围：task（主体）、harness（小扩展）、model-gateway（用量事件）、contracts

## 背景

5.1 已经能「在沙箱里跑一个节点」。5.2 要让 task 服务把一张工作流图跑完：决定哪个节点什么时候跑、拿什么输入、跑完交给谁、出问题怎么办、用户追问发给谁、花了多少钱、用户改了图之后怎么跑。

5.2 里工作流方案由内部接口直接提交（测试和 5.3 的规划都走它）；需求澄清、规划、最终验收、前端在 5.3 和 5.5。

## 决定

### 1. 节点只有两种；「互审」是节点出口上的轻量关卡

| 节点类型 | 做什么 | 运行方式 |
|---|---|---|
| 干活 `work` | 一个 agent 完成一件事，产出文件 | 一次 harness 运行 |
| 讨论 `discussion` | 几个参与者（各自的模型和立场）来回几轮，最后由汇总者写出结论 | 每轮每人一次运行（同一参与者跨轮接着自己的会话），最后汇总一次 |

| 关系 | 表达方式 |
|---|---|
| 串行 | 连线：A → B，A 完成后 A 的产出交给 B |
| 并行 | 互不依赖的节点同时跑（单个任务同时最多 3 个） |
| 讨论 | 讨论节点 |
| 互审 | 不是节点，是节点出口上的关卡：节点交出产出前先过关卡，不过关就带着没满足的地方退回这个节点改一次 |

### 2. 关卡：轻量，有就行（参考 dsh 的门控设计）

dsh 不设常驻的「监工智能体」，而是在阶段边界埋「门」：能用确定性规则判断的用代码判断（stage-gate 的清单），需要语义判断时才临时派一个短命的窄角色给出结构化结论（review-gate）。Oasis 的用户场景大多简单，只取最轻的两层：

1. **规则检查（代码，不花钱）**：`out/` 里有产出；方案里写明的文件都在且不是空的。
2. **验收点检查（Jev，几乎不花钱）**：方案里给这个节点写了验收点（普通话，最多 5 条）时，把节点最后一句话和文字产出（截断到约 8,000 字）交给 Jev，每条验收点问一个「是否满足」。概率低于阈值的算没满足。Jev 只按输入收费，一次约百分之一美分。

- 不过关：带着没满足的验收点，接着这个节点原来的会话改**一次**。改完再查一次，还不过关就照样往下走，但在节点上留一条提醒给用户看，不卡住流程。
- 检查本身出错（Jev 连不上等）：放行，记日志，不卡用户。
- 方案里没写验收点的节点只做规则检查。
- 5.3 的最终验收用同一套关卡，检查对象换成整个任务的交付物。

### 3. 连线：删了中间节点就留下断口

连线是独立的对象，两端各连一个节点，**任一端可以是空的**：

- 删除节点 B（A → B → C）：A → B 变成「A → 空」，B → C 变成「空 → C」。画布上显示为两段断开的线头，不会自动把 A 接到 C。
- 用户可以新建一个节点，把断开的线头接上去；也可以直接从一个节点拉线到另一个节点。
- 一个节点只要有一条进来的线是空的，它就处于「断开」状态，永远不会自动开跑。

连线的规则：

| 操作 | 允许的条件 |
|---|---|
| 新建连线 / 接上线头 | 线的终点必须是还没开始的节点（等待、断开）；起点可以是任何状态的节点，包括已完成的（它的产出交给新节点）；连上后不能成环 |
| 删除连线 | 终点还没开始 |
| 新建节点 | 任务还没结束（结束后要改 = 新任务）。新建的节点是「新建」状态，不会自动开跑，点整体运行或单独运行它才加入 |
| 删除节点 | 节点还没开始；它的进出连线变成断开的线头 |

两种「运行」：

| 用户点的是 | 行为 |
|---|---|
| 某个节点上的「运行」 | 只要这个节点进来的线都接好了、上游都已完成，就只跑这一个节点；已停止的接着做，失败的重新算重做次数再做。任务不在整体运行时（已停止、需要处理），跑完不自动往下 |
| 画布上整个工作流的「运行」 | 先检查整张图：有断开的线头、有环，就提示「工作流有错误」并列出问题，不开跑；没问题就把新建的节点加进来、停下的接着做、失败的再试，从所有可以跑的节点开始一路往下跑 |

工作流跑到一半时用户删掉了还没开始的节点：跑到断口处，那条支路停下，节点显示「断开」；其他支路照常跑。全部能跑的都跑完后，任务停在「需要处理」，等用户接线或取消。

### 4. 状态

节点：

```
新建 ─(点运行)→ 等待
等待 ─(进来的线都接好、上游都完成)→ 运行中 → 检查中（关卡）→ 已完成
  │                                  │        └(不过关，改一次)→ 运行中
  │                                  ├(失败)→ 自动重做，最多 2 次 → 仍失败：任务暂停，问用户
  │                                  └(用户点停止)→ 已停止 ─(继续)→ 运行中（接着原会话）
  └(有空的进线)→ 断开 ─(用户接好线)→ 等待
任何未完成状态 ─(取消任务)→ 已取消
```

- 已完成的节点不能追问、修改、删除，也不会再跑。
- 「停止」和 ChatGPT 里点停止一样：立刻停下，已经做出来的东西和对话都保留；点继续就接着原来的对话往下做。

任务：运行中 / 已停止 / 需要处理（断开、超过重做上限、超过花费上限）/ 已完成 / 失败 / 已取消。

- 停止一个节点时其他支路照常跑；所有能跑的都跑完、只剩停下或新建的节点时，任务变成「已停止」，等用户点运行。
- 停止在 harness 里的做法：不等 AI 说完，直接从还在跑的沙箱里取出产出和会话存档，再销毁沙箱；继续 = 新开一次运行，用 `continueFrom` 接着那次运行（5.2c 实测：中途停下的会话在新容器里能恢复，AI 看得到之前写过的文件和工具结果）。讨论节点停下后继续，是让这一步还没说完的人重新说。

### 5. 节点之间怎么传文件、怎么接着原会话

产出文件 5.1 已存在 harness 的对象存储里。harness 的启动接口加两个可选参数，文件不经过 task：

- `inputsFrom: [{ runId, as }]`：把之前某次运行的产出解到本次沙箱的 `in/<as>/` 下。task 用它把上游节点的产出交给下游（`as` = 上游节点的名字）。
- `continueFrom: runId`：把那次运行的 dsh 会话存档放回沙箱，接着原会话说话。用于关卡不过关后的修改、停止后的继续、讨论里同一参与者的下一轮。

另外三处小改动：
- 运行结束事件 `harness.run.finished` 增加 `summary`（AI 最后一句话）。
- 新增停止接口 `POST /internal/runs/:runId/stop`：先存下产出和会话存档，再销毁沙箱；运行状态记为 `stopped`。
- 新增内部接口：读出某次运行的文字类产出（截断），给关卡检查用。

画布在 5.5 登记最终成果时引用这些运行的产出；中间产物不复制。

### 6. 交给节点的说明怎么拼

由 task 拼好交给 harness：任务单摘要 → 这个节点的角色和目标 → 上游交来了什么（`in/<上游节点名>/` 下的文件清单 + 上游最后一句话）→ 用户对这个节点追加的要求 → 关卡没满足的地方（修改时）→ 固定规则（产出写到 `out/`；不要问用户问题，拿不准的自己做合理决定并在最后说明）。

### 7. 调度、恢复与幂等

- task 订阅 `harness.run.finished`（持久消费者，幂等）。每收到一个就推进对应节点，再找出可以跑的节点启动。
- 启动前先把运行 ID 写进库，再调 harness（harness 对同一运行 ID 幂等）。task 任何时刻崩溃，重启后按库里的状态和 harness 对账：已结束的补上，没提交出去的重新提交。另外每分钟对账一次运行中的节点，防止事件丢失。
- 关卡检查在事务外做，做完再锁住任务推进。检查中途断了（服务重启等），节点停在「检查中」，对账时重新检查。
- 每个任务同时最多跑 3 个节点（`MAX_PARALLEL_NODES`，「检查中」也算在内）；全局并发由 harness 控制。

### 8. 防失控

- 节点失败自动重做最多 2 次；超过就进入「需要处理」，让用户三选一：
  - 用现在的结果继续往下做：这个节点算完成并留提醒，它有产出就交给下游，没有就不交；
  - 再让它试一次：重做次数重新算；
  - 取消任务。
- 花费：model-gateway 每结算一次属于任务的调用（agent 的聊天、关卡的 Jev），就经发件箱发出 `model-gateway.call.settled`（带任务、节点、扣了多少钱）。task 按调用 ID 只算一次，累加到节点和任务上。
  - 上限 = 预估 × 3。任务在跑时花费超过上限：停下所有在跑的节点，进入「需要处理」，用户只能选继续或取消。
  - 选继续（或直接点整体运行）：上限提高到「当前花费 + 预估 × 3」，停下的节点接着做。
  - 预估由 5.3 的规划给出，没有预估就不检查。
- 「需要处理」的原因是连线断开时，用户只能接好线再点运行，或者取消。

### 9. 接口

内部（5.3 的规划、测试用）：`POST /internal/tasks` 提交任务和工作流方案，校验后立即开跑。

对外（经 gateway，5.5 的界面用；只看得到自己的任务）：

| 接口 | 作用 |
|---|---|
| `GET /v1/tasks`、`GET /v1/tasks/:id` | 任务列表；任务详情（节点、连线、状态、花费、提醒） |
| `GET /v1/tasks/:id/nodes/:nodeId/events` | 节点的运行过程（转发 harness 的事件） |
| `POST /v1/tasks/:id/run` | 运行整个工作流（先检查整张图） |
| `POST /v1/tasks/:id/stop`、`/cancel`、`/decision` | 停止全部、取消任务、「需要处理」时选一个 |
| `POST /v1/tasks/:id/nodes` | 新建节点 |
| `PATCH`、`DELETE /v1/tasks/:id/nodes/:nodeId` | 改 / 删还没开始的节点 |
| `POST /v1/tasks/:id/nodes/:nodeId/run`、`/stop` | 运行 / 停止单个节点 |
| `POST /v1/tasks/:id/nodes/:nodeId/messages` | 追问 / 补充要求（运行中、等待、已停止的节点） |
| `POST`、`PATCH`、`DELETE /v1/tasks/:id/edges[/:edgeId]` | 新建连线、接上线头、删除连线 |

### 10. 表（task 库，全部是新表，expand）

| 表 | 内容 |
|---|---|
| `tasks` | 所有者、付费人、来源会话、标题、任务单（JSON）、状态、需要处理的原因、预估花费、已花费、花费上限、时间 |
| `nodes` | 所属任务、节点名、显示名、类型、角色、目标、模型、配置（讨论参与者与轮数、验收点、应有的文件、产出来自哪次运行）、状态、重做次数、用户追加要求、提醒、最近一次运行、已花费、时间 |
| `edges` | 所属任务、起点节点（可空）、终点节点（可空） |
| `node_runs` | 节点的每一次运行：运行 ID、用途（干活 / 发言 / 汇总 / 修改）、第几次、状态、AI 最后一句话 |
| `spend_records` | 已经计入花费的模型调用（调用 ID 为主键）：结算事件可能重复到达，按调用只算一次。不能放进 `tasks` / `nodes`，因为幂等要按每次调用记 |
| （不建 `processed_events`） | 消费 `harness.run.finished` 的幂等靠 `node_runs` 的状态：已结束的运行再收到一次直接跳过。task 要发事件（5.3 通知私聊）时再建 `outbox` |

model-gateway 新增 `outbox`（发用量事件）。

### 11. 5.2 的拆分与待确认

| 步骤 | 内容 |
|---|---|
| 5.2a | 表、方案校验、串行 / 并行调度、上游产出传递、失败自动重做、取消、追问路由、崩溃恢复；harness 加 `inputsFrom` / `summary` |
| 5.2b | 讨论节点、关卡（规则检查 + Jev 验收点 + 改一次）；harness 加 `continueFrom` 和文字产出读取 |
| 5.2c | 停止 / 继续、建 / 改 / 删节点、连线与断口、单节点运行与整体运行前检查、「需要处理」、用量事件与花费上限 |

用户已确认（2026-10-22）：
- 关卡改一次还不过关时，照样往下走、只留提醒（而不是停下来问用户）。
- 单节点运行只跑这一个节点，跑完不自动往下；要往下跑就点整体运行。

5.2b 实现时定下的细节：
- 讨论：每轮所有参与者并行发言（这些发言算在同一个节点里，不受 3 个并发的限制）；某人的发言失败，只重做他这一句；重做次数整个节点共用（最多 2 次），用完还失败就停掉同一轮其他人的发言，任务进入「需要处理」。
- 讨论进行中的追问：记下来，下一轮发言和汇总时带上（讨论不是单个会话，没法插话）。
- 「检查中」的节点不能追问。
- 修改（`rework`）失败时从头再做一次，之后照常过关卡；修改次数已经用掉，再不过就留提醒。
- 配置：`GATE_MODEL`（默认 `typesafe/jev-1.14`）、`GATE_THRESHOLD`（默认 0.5）、`MAX_NODE_REWORKS`（默认 1）。

5.2c 实现时定下的细节：
- 用户新建的节点先是「新建」状态，不自动开跑（否则还没接线就会被调度器拿去跑）。
- 上游没有产出文件时，下游拿不到它的东西（不再引用它的运行）。下游拿的是「交出现在这份产出的那次运行」：关卡退回修改后，就是修改那次。
- 关卡调用 Jev 时带上任务和节点（`x-oasis-task-id` / `x-oasis-node-id`），花费计入任务。
- 配置：`BUDGET_MULTIPLIER`（默认 3）。

5.2 结束时用真实 DeepSeek 跑一个「两个节点并行写 → 讨论 → 汇总」的小工作流，预计花费 1 美分以内，跑之前先问用户。

## 后果

- 文件留在 harness 的对象存储里，不经过 task；代价是画布（5.5）要通过 harness 读取产出。
- 讨论节点的运行次数 = 参与者数 × 轮数 + 1，花费随之增长；预估花费（5.3）要把这个算进去。
- 关卡只做轻量检查：放过一些质量问题是有意的取舍，换来的是不额外花钱、不拖慢简单任务。
