# ADR 0004：工作流控制面（5.2）

- 状态：草案（2026-10-22），待用户确认
- 依据：ADR 0003（产品规则、五道门、四种节点关系）、5.1 已落地的 harness 与 model-gateway
- 范围：task（主体）、harness（小扩展）、model-gateway（用量事件）、contracts

## 背景

5.1 已经能「在沙箱里跑一个节点」。5.2 要让 task 服务把一张工作流图跑完：决定哪个节点什么时候跑、拿什么输入、跑完交给谁、出问题怎么办、用户追问发给谁、花了多少钱。

5.2 里工作流方案由内部接口直接提交（测试和 5.3 的规划都走它）；需求澄清、规划、验收、前端在 5.3 和 5.5。

## 决定

### 1. 节点的种类和四种关系

一个节点有三种类型。四种关系用它们组合出来：

| 类型 | 做什么 | 运行方式 |
|---|---|---|
| 干活节点 `work` | 一个 agent 完成一件事，产出文件 | 一次 harness 运行 |
| 讨论节点 `discussion` | 几个参与者（各自的模型和立场）来回几轮，最后由汇总者写出结论 | 每轮每人一次运行，最后汇总一次；同一参与者跨轮接着自己的会话 |
| 审查节点 `review` | 对照标准检查一个或几个目标节点的产出，给出「通过 / 不通过 + 要改什么」 | 一次运行，必须写出 `out/verdict.json` |

| 关系 | 表达方式 |
|---|---|
| 串行 | 依赖：B 依赖 A，A 完成后 A 的产出交给 B |
| 并行 | 互不依赖的节点同时跑（单个任务同时最多 3 个，可配置） |
| 讨论 | 讨论节点 |
| 互审 | 审查节点指向目标节点。「互相挑错」= 两个审查节点交叉指向对方的干活节点，审查者用对方的模型和角色 |

### 2. 状态机（「已完成不可修改」与「互审打回」不冲突）

```
等待 ─(依赖都完成)→ 运行中 ─(有审查)→ 待审 ─(通过)→ 已完成
                     │                 └(不通过)→ 运行中（带着修改意见接着原会话改，算一次重做）
                     ├(没有审查)────────────────→ 已完成
                     ├(失败)→ 自动重做，最多 2 次 → 仍失败：任务暂停，问用户
                     └(用户暂停)→ 已暂停 ─(继续)→ 运行中（接着原会话）
任何未完成状态 ─(取消任务)→ 已取消
```

- 只有「通过审查」或「没有审查」才进入「已完成」；已完成的节点不能追问、修改、删除，也不会再跑。
- 审查打回超过上限（默认 2 轮）：任务暂停，问用户（见第 6 节）。
- 任务状态：运行中 / 已暂停（含「等用户决定」）/ 已完成 / 失败 / 已取消。所有节点完成即任务完成（5.3 再在此之后接验收门）。

### 3. 节点之间怎么传文件、怎么接着原会话

产出文件 5.1 已存在 harness 的对象存储里。5.2 给 harness 的启动接口加两个可选参数，文件不经过 task：

- `inputsFrom: [{ runId, as }]`：把之前某次运行的产出解到本次沙箱的 `in/<as>/` 下。task 用它把上游节点的产出交给下游（`as` = 上游节点的名字）。
- `continueFrom: runId`：把那次运行的 dsh 会话存档放回沙箱，接着原会话说话。用于审查打回后的重做、暂停后的继续、讨论里同一参与者的下一轮。

另外两处小改动：
- 运行结束事件 `harness.run.finished` 增加 `summary`（AI 最后一句话），下游节点和界面要用。
- 取消接口增加「暂停」方式：先存会话存档，再销毁沙箱。

画布在 5.5 登记最终成果时引用这些运行的产出；中间产物不复制。

### 4. 交给节点的说明怎么拼

由 task 拼好交给 harness，内容依次是：

1. 任务单摘要（5.3 前由提交方直接给）。
2. 这个节点的角色和目标。
3. 上游交来了什么：`in/<上游节点名>/` 下的文件清单，加上游最后一句话。
4. 用户对这个节点追加的要求（节点还在等待时用户写的）。
5. 审查意见（重做时）。
6. 固定规则：产出写到 `out/`；不要问用户问题，拿不准的自己做合理决定并在最后说明。

### 5. 调度、恢复与幂等

- task 订阅 `harness.run.finished`（持久消费者，幂等）。每收到一个，就推进对应节点，然后找出依赖都已完成的节点并启动。
- 启动前先把运行 ID 写进库，再调 harness（harness 对同一运行 ID 幂等）。这样 task 在任何时刻崩溃，重启后都能按库里的状态对账：运行中的节点去 harness 查一下结局，已结束的补上，没提交出去的重新提交。
- 每个任务同时最多跑 3 个节点（`MAX_PARALLEL_NODES`）；全局并发由 harness 控制。

### 6. 防失控

- 节点失败自动重做最多 2 次；审查打回最多 2 轮。超过就暂停任务，状态记为「等用户决定」，给用户三个选择：
  - 用现在的结果继续往下做；
  - 再让它试一次；
  - 取消任务。
- 花费：model-gateway 每结算一次调用，就经发件箱发出 `model-gateway.call.settled`（带任务、节点、扣了多少钱）。task 订阅后累加到节点和任务上。实际花费超过预估的 3 倍时暂停任务，问用户。预估由 5.3 的规划给出，没有预估就不检查。

### 7. 用户在节点上的操作

| 节点状态 | 追问 / 补充要求 | 修改目标 | 删除 | 暂停 / 继续 |
|---|---|---|---|---|
| 等待 | 记下，开跑时带上 | 可以 | 可以：它的下游改为直接依赖它的上游 | — |
| 运行中 | 直接插进它的会话，只影响这个节点 | — | — | 可以暂停 |
| 待审 | 不行（审查员正在看） | — | — | — |
| 已暂停 | 记下，继续时带上 | — | — | 可以继续 |
| 已完成 / 已取消 | 不行 | 不行 | 不行 | — |

- 删除只能删整个任务（连同中间产物）；单个节点只有在「等待」时能删。
- 修改不往后传：后面的节点照样拿这个节点交出来的东西，除非用户自己去改后面的节点。

### 8. 接口

内部（5.3 的规划、测试用）：
- `POST /internal/tasks`：提交任务和工作流方案，校验后立即开跑。

对外（经 gateway，5.5 的界面用；只看得到自己的任务）：
- `GET /v1/tasks`、`GET /v1/tasks/:id`（含全部节点、状态、花费）。
- `GET /v1/tasks/:id/nodes/:nodeId/events`：节点的运行过程，转发 harness 的事件。
- `POST /v1/tasks/:id/pause | resume | cancel`。
- `POST /v1/tasks/:id/decision`：「等用户决定」时选一个。
- `POST /v1/tasks/:id/nodes/:nodeId/messages`：追问 / 补充要求。
- `PATCH /v1/tasks/:id/nodes/:nodeId`、`DELETE /v1/tasks/:id/nodes/:nodeId`：改 / 删等待中的节点。
- `POST /v1/tasks/:id/nodes/:nodeId/pause | resume`。

方案的校验规则：节点名唯一；依赖和审查目标都存在；除审查回路外没有环；每个节点都有模型；讨论至少 2 个参与者、1–5 轮；审查最多 3 轮。

### 9. 表（task 库，全部是新表，expand）

| 表 | 内容 |
|---|---|
| `tasks` | 所有者、付费人、来源会话、标题、任务单（JSON）、状态、等用户决定的原因、预估花费、已花费、时间 |
| `nodes` | 所属任务、节点名、显示名、类型、角色、目标、模型、配置（讨论参与者 / 审查目标与标准 / 轮数）、依赖、状态、重做次数、审查轮次、用户追加要求、最近一次运行、已花费、时间 |
| `node_runs` | 节点的每一次运行：运行 ID、用途（干活 / 发言 / 汇总 / 审查）、第几次、状态、AI 最后一句话、审查结论 |
| `processed_events`、`outbox` | 幂等消费、事务发件箱（与其他服务相同） |

model-gateway 新增 `outbox`（发用量事件）。

### 10. 5.2 的拆分

| 步骤 | 内容 |
|---|---|
| 5.2a | 表、方案校验、串行 / 并行调度、上游产出传递、失败自动重做、取消、追问路由、崩溃恢复；harness 加 `inputsFrom` / `summary` |
| 5.2b | 讨论节点、审查节点与打回重做；harness 加 `continueFrom` |
| 5.2c | 暂停 / 继续（节点与任务）、改 / 删等待中的节点、「等用户决定」、用量事件与花费上限 |

每一步都用假模型跑完整测试；5.2 结束时用真实 DeepSeek 跑一个「两个节点并行写 → 一个节点汇总 → 一个审查」的小工作流，预计花费 1 美分以内，跑之前先问用户。

## 后果

- 文件留在 harness 的对象存储里，不经过 task，task 的数据库保持很小；代价是画布（5.5）要通过 harness 读取产出。
- 讨论节点的运行次数 = 参与者数 × 轮数 + 1，花费随之增长；预估花费（5.3）要把这个算进去。
- task 依赖 harness 的事件推进，事件丢失时靠启动对账和定时对账（每分钟查一次运行中的节点）兜底。
