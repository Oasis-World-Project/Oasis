# 文档类

> 适用：交付物主要是文字——文案、文章、报告、方案、说明、简历、邮件、脚本、提纲……

## 一般怎么分工

- 一两份短文案：1 个干活节点写完就够，交付物就是它的产出。不要为了显得完整而拆成「写—审—改」三段，节点出口已经有关卡检查。
- 需要事实、数据或最新信息的：先一个「查资料」节点（工具 `web.search`、`web.fetch`，各用 2–4 次），把要点和出处写成 `out/资料.md`，再连到写作节点。
- 需要在几个方向里挑的（品牌口号、标题、开头）：2–3 个写作节点并行写不同方向，接一个讨论节点比较取舍，由它写出定稿；或者写作节点自己用 `jev.decide` 在几个候选里挑一个。
- 长文档（报告、方案）：一个节点先写提纲 `out/提纲.md`，再按章节拆成几个并行节点写，最后一个节点合并统稿。章节不超过 4 个。

## 工具

- `web.search` / `web.fetch` 只在需要最新信息、具体数据、引用出处时用；常识和创作不用。
- `jev.decide` 几乎不花钱，适合「这几个候选哪个更好」。

## 交付物

- 默认 Markdown，文件名用交付物的名字，如 `out/首页文案.md`。
- 用户要 Word 或 PDF：写作节点照常交 Markdown，再由下游节点用 Python 生成（`pip install python-docx` 或 `reportlab`，沙箱里能装包），expects 写上 `*.docx` / `*.pdf`。

## 常见的坑

- 字数、语气、必须包含的要点写进 goal，并让节点交付前自己核对一遍。
- checks 只挑能从文字判断的验收点（语气、要点、结构），不要放「用户满意」这种判断不了的。
- 查资料节点要写明每条信息的出处网址；写作节点不得编造数据，拿不准的写成「待确认」。
